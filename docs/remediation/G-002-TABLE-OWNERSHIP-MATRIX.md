## Purpose and evidence boundary

This inventory is derived from the Drizzle schema modules re-exported by apps/api/src/drizzle/schema.ts on the reviewed branch. It names **99 tables across the exported Drizzle schema modules**.

It is not the complete live database inventory. The detailed 19-November catalog report and 21-November Drizzle reconciliation agree on 114 public relations: 99 Drizzle table declarations plus 15 non-Drizzle/partition relations. A separate 116-table count appears in earlier/summary wording, but its scope is not reconciled against the detailed 114-relation inventory. Treat 114 as the last detailed public-schema snapshot, keep the 116 discrepancy open, and refresh the protected catalog audit before using either count as a current total. Raw-SQL-only tables, extensions, partitions, views, or objects in other schemas may not appear in the Drizzle export.

The scope descriptions below are candidate row-ownership models, not verified direct column predicates. They must not be translated mechanically into policies. Exact owner columns, foreign-key paths, route/service operations, worker access, and write semantics still require source and migration inspection.

## Required completion fields for each table

Before a row is marked policy-ready, add and verify all of the following from source and migrations:

1. Physical schema/table name, object kind (table, partition, view, materialized view), owning migration, and whether it is present in the Drizzle export.
2. Exact direct owner columns, nullable behavior, FK target and full inherited ownership path. Record actual FK constraint names and ON DELETE behavior.
3. Every API route, controller, service and repository operation that performs SELECT, INSERT, UPDATE or DELETE; include raw SQL and joins.
4. Every non-HTTP path: outbox/worker, scheduler, webhook, audit middleware, import, bootstrap, maintenance and migration.
5. Principal classes and exact predicates: anonymous, buyer, merchant owner, merchant staff, finance, support, platform administrator, and service worker. Do not assume role names imply access.
6. Public projection rules, lifecycle/state filters, sensitive fields, immutable/audit requirements, and whether a record contains secrets, identity evidence, payment data or raw operational payloads.
7. Required SQL privileges separately from row predicates; sequence/function privileges; views/functions/triggers; partitions; FK cascade behavior; and default ACL impact.
8. Positive and negative tests on a non-owner role with NOSUPERUSER, NOBYPASSRLS, NOCREATEDB and NOCREATEROLE, including pool reuse and rollback.
