## Purpose and evidence boundary

This document records ownership paths visible in the Drizzle schema definitions reviewed for identity, merchant, catalog, taxonomy, orders/cart/shipment, payments, returns, promotions, inventory, pricing, notifications, audit, reviews/disputes, shipping, catalog imports and operations.

The classifications are **predicate candidates**, not policy expressions. A column's presence in a schema does not prove the corresponding database foreign-key constraint exists; some UUID fields are not declared with Drizzle `.references()`. Confirm every relationship against the actual migration/catalog constraint before writing SQL policies. Also inspect service-level checks and controller principals: an ownership column does not by itself define who may read or mutate a row.

## Ownership classes

| Class        | Meaning                                                    | Candidate access principal                                                          |
| ------------ | ---------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| PLATFORM     | Global reference/configuration or platform governance data | Explicit platform service/admin capability; no tenant-wide access by default        |
| ORGANIZATION | Root organization-owned row                                | Active organization membership with the required role/permission                    |
| STORE        | Store-owned row                                            | Active membership in the owning store, constrained through its organization         |
| BUYER        | User-private or buyer-owned row                            | Owning user; for order-linked rows, also the relevant order participant rules       |
| ORDER        | Child row inheriting access from an order/suborder         | Resolve parent order, then apply buyer/store participant and lifecycle policy       |
| PARENT       | Child row inheriting access from a parent record           | Resolve parent chain; do not assume a direct org field                              |
| SYSTEM       | Worker lease, control, alert, outbox or operational state  | Explicit worker/system or platform-operator context                                 |
| MIXED        | Multiple ownership/actor references or cross-domain row    | Use the domain-specific relationship and action; no single generic tenant predicate |

## Critical design conclusions

1. **No universal org_id predicate is safe.** Many rows have no org column and inherit access through a parent chain; others are global taxonomy, user-private, multi-party orders or system records.
2. **Order is a multi-principal boundary.** Buyer and store can both have legitimate access to different columns/actions, while children inherit from the exact parent order. Driver access is separately assignment-scoped.
3. **Membership edges are first-class authorization data.** organization_members and store_members must be checked for status, role and active organization/store. A JWT permission claim alone does not prove current membership.
4. **Cross-reference consistency is part of tenant isolation.** For example, merchant_offers.price_list_id and warehouse_id must resolve to the same store; price tiers must not combine a foreign price list with a variant; delivery_zone_methods must connect same-store parents; order items/refunds/returns must remain attached to the same order and payment lineage.
5. **Global catalog data needs an explicit governance model.** Null-store products/categories, brands, attribute definitions/options/groups, product types and trust aggregates cannot be assigned tenant ownership by guesswork.
6. **Worker/system rows need dedicated context.** Outbox, carrier webhook, leases, controls, alerts and global reconciliation must not inherit an arbitrary HTTP request's tenant identity.
7. **Audit actor fields are not owner fields.** uploaded_by, created_by, reviewed_by, actor_id, performed_by, resolved_by and similar fields record attribution. Do not use them as the sole row-visibility predicate.
8. **Schema declarations are not the live catalog.** The table count, FK constraints, nullability, partitions, views/functions/sequences and migration-created objects still need the protected read-only catalog reconciliation. The 114-versus-116 discrepancy remains open.

## 25 November 2026 — source-level Catalog predicate follow-up

The Catalog source now has additional operation-specific predicates, without changing the evidence boundary of this candidate inventory:
- Store-owned category list/search/detail surfaces require active org/store membership; default/public category discovery and tree are active platform-only.
- Product category assignments and category parent links require active global or same-store ownership. Product types are global and reject tenant/inactive category references on write, publish, duplicate and version; public reads exclude legacy tenant-bound bindings.
- Product update/type-change/delete/bulk writes repeat the store owner and non-deleted predicate. Media deletion includes both media and parent product IDs.
- Offer lifecycle writes compare current status and owner store; pricing compares updatedAt. Request review locks the pending request under a verified user transaction and transitions only PENDING rows.
- Public facet values are derived only from published product types in active platform categories and ACTIVE/non-deleted products.

These are source-level changes and regression specs only. They do not prove deployed constraints, existing row consistency, or the protected live catalog.
