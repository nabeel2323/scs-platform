2. Architecture & Module Boundaries

The backend is a modular monolith: one deployable, one database, with strictly enforced bounded contexts. Each NestJS module owns its tables, its domain events and a single public application service. Modules never read another module's tables — they call exported services or react to events.

2.3 Boundary rules (CI-enforced)

  1. Service-only cross-module calls — never import another module's repo or touch its tables.
  2. Side effects via the outbox — write outbox_events in the same transaction; never fire-and-forget.
  3. Read models are built by the consumer from events, not by joining another module's tables.
  4. Public contracts are versioned in packages/contracts (OpenAPI → generated TS/Dart).
  5. Extraction only on a trigger — scale divergence, team boundary or fault isolation. Until then: one database, one deployable.
Reality check

The packages/contracts codegen boundary is aspirational: today web/admin hand-roll API clients and mobile re-declares JSON shapes. This is the single largest drift risk (see §11).

4. Data Flow & the Transactional Outbox

State changes are the heart of the platform. Every mutation follows one transactional unit so that the database and the event stream can never diverge:

sequenceDiagram participant C as Client participant Ctrl as Controller participant Svc as Application Service participant DB as PostgreSQL (tx) participant OB as outbox_events participant D as OutboxDispatcher (1s) participant H as Consumers (notifications/analytics/inventory/realtime) C->>Ctrl: POST /v1/... (JWT + Idempotency-Key) Ctrl->>Svc: delegate (thin controller) Svc->>DB: BEGIN — guard → mutate → history row Svc->>OB: INSERT outbox event (same tx) DB-->>Svc: COMMIT Svc-->>C: 200/201 (RFC 7807 on error) D->>OB: poll unpublished D->>H: fan-out domain event H-->>D: ack → mark published

4.1 Why the outbox

  • Atomicity — the business row and its event commit together; no "updated but not notified" states.
  • At-least-once delivery — the dispatcher retries until a consumer acks; consumers must be idempotent.
  • Future extraction — the event log is the seam along which a module (notifications first) can later become a service.

4.2 Request lifecycle & cross-cutting middleware

  1. Helmet security headers → request-ID correlation → Pino structured log line {ts,level,reqId,module,userId?,orgId?,msg}.
  2. JWT guard validates the access token (15-min TTL); @RequirePermission() adds RBAC where declared.
  3. Org-scope guard restricts merchant/admin reads to the actor's active organisation.
  4. Validation pipe (forbidNonWhitelisted) — effective only where DTOs exist (see §11).
  5. AllExceptionsFilter renders every failure as RFC 7807 application/problem+json.

5.2 Canonical transition implementation

// orders.service.ts — every transition is a single transactional unit
async transition(orderId, to, actor, reason?, idemKey?) {
  return this.db.transaction(async (tx) => {
    await this.idem.seenOrReplay(idemKey, tx);                 // 1. idempotency
    const order = await tx.repo.orders.lockForUpdate(orderId);   // 2. row lock — no lost transitions
    const guard = this.fsm.guard(order.status, to);             // 3. FSM guard — only source of truth
    if (!guard.allowed) throw new InvalidTransitionProblem(order.status, to);
    await guard.sideEffects(tx, order, actor);                  // 4. reserve/release stock, re-price, webhook
    await tx.repo.orders.setStatus(orderId, to);
    await tx.repo.statusHistory.insert({ orderId, from: order.status, to, actor, reason });
    await tx.repo.outbox.insert({                               // 5. exactly one event
      aggregateType: 'order', aggregateId: orderId,
      eventType: 'order.status.changed',
      payload: { orderId, from: order.status, to, at: new Date() },
    });
  });
}

Rules encoded once, reused everywhere: no controller calls a repo directly; no transition bypasses transition(). Both the service matrix and the mobile FSM (merchant_orders_screen.dart) are aligned. resolveStatusAlias() maps legacy CONFIRMED → PENDING_CONFIRMATION for backward compatibility.

5.3 Policies

  • Re-price guard: if the price list changed between checkout and acceptance, acceptance returns 409 price_changed with per-line deltas; the merchant confirms each changed line.
  • Idempotency: all transition endpoints accept Idempotency-Key; replays return the original result, never a second transition.
  • SLA timers: a delayed job fires at sla_at − 2h (order.sla.warning) and at sla_at (auto-CANCELLED, reason SLA_EXPIRED).
  • Partial cancellation: only the affected sub-order changes; master_orders.status is derived worst-of (any DISPUTED → master DISPUTED).
  • Dispute window: 72h from DELIVERED; opening freezes finalized_at (P3: freezes settlement lines).

6. API Contracts

6.1 Conventions

  • REST over HTTPS at /v1, JSON, camelCase. Errors are RFC 7807 application/problem+json with a stable type URI per error family.
  • Idempotency-Key header required on POST /v1/checkout, all order state transitions, and (P3) payment intents — Redis-backed 24h store; identical replay returns the original result.
  • Cursor pagination (?limit=50&cursor=); filters/sorts whitelisted per endpoint; optimistic concurrency via If-Match ETag on catalog/admin mutations.
  • Rate limits: Redis token bucket per user/IP/role with X-RateLimit-* headers; OTP endpoints additionally throttle by phone number (5 / 15 min).

7. Data Model & Migrations

7.2 Money, pricing & the financial breakdown

Orders carry an order_financial_breakdown that is shadow-populated from Phase 1 so Phase 3 activates it rather than retrofitting. Line items snapshot SKU, title and unit price at checkout so later catalog edits never mutate history.

Live defect — pricing not applied (API-B4)

In orders.service.ts the checkout totals still hardcode discount = 0, deliveryFee = 0, tax = 0 (lines 104–106). Promo codes are stored on the order but never priced, and 15% KSA VAT is unapplied. This is the top open P1 correctness gap for transactions.

7.3 Identity & roles

Role keys are seeded as SUPER_ADMIN, ADMIN, MODERATOR, MERCHANT_OWNER, MERCHANT_STAFF, BUYER — there is no generic OWNER/MEMBER key. Org creation awards MERCHANT_OWNER; joining by invite code awards MERCHANT_STAFF. Organizations carry a unique 12-char invite_code.

8. Authentication & Security

8.1 Dual-auth with device trust

sequenceDiagram participant U as User (web/mobile) participant A as API identity participant R as Redis participant DB as sessions U->>A: POST /auth/otp/request {phone} A->>R: store otp phone (dev: no SMS) U->>A: POST /auth/otp/verify {phone, otp, deviceId} A->>DB: create session WITH device_id (device trust) A-->>U: accessToken(15m) + refreshToken (rotating) Note over U,A: Later, on a trusted device U->>A: POST /auth/login {phone, password, deviceId} A->>DB: device_id matches a trusted session? alt trusted A-->>U: tokens (no OTP) else new device A-->>U: requiresOtp step-up end
  • Passwords: bcrypt cost 12, NIST-aligned rules, credential_audit_log.
  • OTP: codes in Redis key otp:<phone> (dev emits to Redis, not SMS); rate limit 5/15 min; typed 401/429 (was HTTP 500).
  • JWT: 15-min access + rotating refresh with reuse detection (revokeChain on replay).
  • Device trust: deviceId persisted on the session at OTP verify (fixed 2026-09-04) — ends the infinite-OTP loop on new-device password login.

8.2 RBAC posture

Authorisation uses a JWT guard everywhere plus a @RequirePermission() decorator for fine-grained rights. Current coverage: 19 usages — 15 in admin.controller.ts (admin:*), 3 merchant verification-review, 1 catalog brands.

Open — merchant write RBAC (API-B6)

Merchant/catalog write endpoints (products, orders, promotions, store mutations) rely on the JWT + org-scope guard alone, with no explicit permission keys. Recommended: seed merchant:products:write, merchant:orders:write, merchant:promotions:write and annotate the write routes.

8.3 Hardening checklist

  • Done CORS allows X-Device-Id (preflight 204 verified).
  • Done Typed auth errors (RFC 7807) instead of generic 500s.
  • Done Daily Postgres backup + restore drill (infra/backup/).
  • Open Production config gate: fail fast if JWT_ACCESS_SECRET unset outside dev.
  • Open DTOs for all auth bodies so forbidNonWhitelisted actually filters.
  • Open switchOrg re-signs the JWT but does not revoke the old access token (≤15-min stale-permission window).

10. Extending the Platform

10.1 Add a new API endpoint (existing module)

  1. Adjust the Drizzle table in <module>.schema.ts and add a migration in infra/drizzle/migrations/.
  2. Implement the use case in <module>.service.ts (the only public surface); keep queries in <module>.repo.ts.
  3. If it mutates state, write an outbox_events row in the same transaction — never call another module directly.
  4. Expose a thin route in <module>.controller.ts; add @RequirePermission() for writes; require Idempotency-Key for order/payment mutations.
  5. Extend the matching client contract in the same commit (buyer-api.ts, admin/src/lib/api.ts, or mobile/lib/services/api_service.dart).

10.2 Add an admin console page

apps/admin/src/app/<feature>/page.tsx     # the screen
apps/admin/src/lib/api.ts                  # append typed fetch helpers

10.3 Add a mobile screen

  1. Create mobile/lib/screens/<area>/<name>_screen.dart (ConsumerWidget / ConsumerStatefulWidget).
  2. Add API methods to lib/services/api_service.dart and models to lib/models/models.dart.
  3. Expose data via a provider in lib/providers/providers.dart.
  4. Register a GoRoute in lib/router/router.dart and link it from a hub/home card.
  5. Use DropdownButtonFormField(initialValue: ...) (not the deprecated value:); guard dropdown values against the items list.

10.4 Add a whole new module

Create modules/<ctx>/ with the uniform layout (2.2), register it in the app module, own its tables and events, and add a CODEOWNER. Do not read another module's tables — consume its events and build a local read model.

Definition of Done (every story)

Compiles clean (tsc --noEmit / dart analyze 0 issues) · migration in the canonical folder · contracts extended in the same commit · outbox event for any state change · tests for the happy + one failure path · boundary lint green.

11.2 Conventions to preserve
