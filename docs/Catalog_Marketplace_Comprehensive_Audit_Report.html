1. Executive Summary

Overall Assessment: The backend architecture is launch-ready for Phase 1–4 of the marketplace catalog evolution (canonical products, attributes, product types, merchant offers). The domain model, API surface, RBAC, migrations, and test infrastructure are solid. However, the frontend has significant gaps — most admin governance pages are stubs, the buyer experience lacks dynamic variant selection and offer comparison, and the merchant product creation workflow is not yet template-driven.

3.3 Known Backend Gaps

BK-1: products.storeId still NOT NULL P0

The products table still requires storeId. For a true canonical product (platform-owned, multi-merchant), this must be nullable. Migration 0025 relaxes at DB level but the ORM type still says notNull().

BK-2: No merchant request workflow API P1

§31 requires merchants to request new categories, brands, attributes. No tables, endpoints, or status machine exist.

BK-3: Conditional attribute rules not enforced P1

conditionalRules jsonb column exists on productTypeAttributes but no runtime validation evaluates these rules during product creation or publishing.

BK-4: No product completeness / data quality scoring P2

§65 calls for a completeness score. No backend computation exists.

5. Missing Features — Prioritized

P0 — Launch-Blocking

M-01: Admin Product Type Builder §33, §69

The flagship admin tool for managing product types, their attributes, groups, validation rules, variant dimensions, and preview has zero UI. The API is complete (catalog.taxonomy.controller.ts) but administrators cannot use it.

Effort: 8–10 days · Dependencies: None (API ready)

M-02: Admin Attribute Management UI §32

No admin page to create/edit/deprecate attribute definitions or manage attribute options. The API exists (POST/PATCH/DELETE admin/attributes) but has no UI.

Effort: 3–4 days · Dependencies: None

M-03: Dynamic Variant Selector on Buyer Product Page §35–36

The buyer sees a flat list of all variants instead of a dynamic matrix (e.g., RAM × Storage × Color) that disables unavailable combinations. This is the core marketplace UX.

Effort: 4–5 days · Dependencies: Product type variant dimensions API

P1 — Critical

M-04: Offer Comparison Table §37–38

"Other Sellers" is a list, not a structured comparison. Buyers need to compare price, MOQ, stock, lead time, shipping, warranty side-by-side.

Effort: 3–4 days

M-05: Admin Offer Governance Workflow UI §48

The offers admin page is a generic table. The approve/reject/suspend/activate API endpoints exist but the admin UI doesn't surface these actions.

Effort: 2–3 days

M-06: Template-Driven Merchant Product Creation §27–28, §70

Merchants currently use a flat product form. The spec requires a step-based wizard that dynamically generates fields from the Product Type configuration.

Effort: 6–8 days

M-07: Variant Matrix Generator for Merchants §21

Merchants need a UI to select variant dimensions (e.g., RAM × Storage × Color), see all theoretical combinations, and disable ones they don't sell.

Effort: 4–5 days

M-08: B2B Buying Actions (RFQ, Bulk Inquiry, Contact Supplier) §63

No RFQ, bulk pricing request, contact supplier, or sample request functionality exists anywhere in the UI.

Effort: 5–6 days (API + UI)

M-09: Merchant Request Workflow §31

Merchants cannot request new categories, brands, attributes, or attribute options. No API or UI exists.

Effort: 4–5 days (API + UI)

M-10: products.storeId NOT NULL Constraint §17

The products table still requires storeId at the ORM level. For true canonical products (platform-owned, multi-merchant), this must be nullable.

Effort: 1–2 days (migration + service updates)

P2 — Nice-to-Have

M-11: Product Comparison UI §43

Side-by-side comparison of products within compatible product types using normalized attributes. Effort: 4–5 days.

M-12: Data Quality Dashboard §64–65

Admin dashboard showing products missing attributes, duplicate candidates, incomplete media, completeness scores. Effort: 5–6 days.

M-13: SEO Structured Data §67

No JSON-LD structured data on product pages. No canonical URL management. Effort: 2–3 days.

M-14: Conditional Attribute Rules Enforcement §15

conditionalRules jsonb exists but is never evaluated. Backend validation + frontend form integration needed. Effort: 3–4 days.

M-15: GTIN/EAN Dedup Admin Review Workflow §44, §60

Identifiers exist on products but no admin workflow to review/merge duplicate candidates. Effort: 3–4 days.

M-16: Mobile Catalog Parity §61–62

Mobile app lacks offer comparison, dynamic variant selection, template-driven creation, typed API client for catalog. Effort: 8–10 days.

M-17: Admin Audit Log Page §32

The audit page is a 5-line stub. The backend audit service and audit:read permission exist. Effort: 2–3 days.

8.2 Security Gaps

S-01: Mobile API Client Missing Catalog Types P1

The Flutter api_client package only covers auth/profile models. Catalog, offer, and order types are hand-written in models.dart (972 lines), creating contract drift risk.

S-02: Some Admin Pages Lack Granular Permission Checks P1

The admin sidebar gates navigation on permissions, but the generic ManagementPage uses a single permission per entity. Offer governance actions (approve/reject/suspend) require catalog:offers:govern but the offers page doesn't surface these actions in the UI.

S-03: No CSRF Protection on State-Changing GETs P2

Some read routes are authenticated but not permission-gated (by design for merchant/buyer rendering). State-changing routes all use POST/PATCH/PUT/DELETE with proper guards.
