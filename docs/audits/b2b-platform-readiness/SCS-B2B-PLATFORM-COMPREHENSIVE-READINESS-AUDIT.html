1. Executive summary

The current codebase is a substantial multi-merchant marketplace implementation, not a blank or early prototype. It contains real organization, catalog, offer, inventory, cart, parent/sub-order, payment-record, shipping, return, dispute, administration, and mobile code. However, it is not ready for commercial launch because at least one authenticated cross-tenant read path is not properly scoped, the database has no RLS protection, a shared outbox consumer can consume carrier events without executing them, and several buyer-facing pricing/checkout paths do not preserve the selected commercial terms.

What buyers can do in source: authenticate, manage organization context, search products, compare seller offers on product detail pages, maintain carts, and submit multi-supplier checkout. Web and mobile both have order views. Web checkout supports per-store shipping selections; mobile currently sends one global fulfillment choice.

What merchants can do in source: register, manage stores and employees, submit verification, manage products and offers, view offer analytics, manage inventory, and process supplier sub-orders. Some offer analytics endpoints lack tenant authorization, so the existence of merchant screens does not imply secure merchant boundaries.

What administrators can do in source: manage users, merchants, products, catalog taxonomy, imports, orders, payment verification, refunds, settlements, and selected operational queues. A generic management surface supports search, filters, pagination, and detail dialogs; specialized flows exist for catalog import and payment operations.

What is not established: full browser-based buyer and merchant journeys, live Aramex transactions, live SMS/FCM/WhatsApp delivery, external payment-gateway settlement, production backup/restore, and current Render OTP logs. These remain NOT VERIFIED rather than being treated as successful.

Launch blocker: GET /v1/merchant/offers, /analytics, and /analytics/trend accept a caller-supplied store ID but do not enforce merchant membership/tenant scope. The service returns offer and sales data using that store ID. An authenticated user may therefore be able to read another merchant's offer portfolio and sales analytics.

5. Architecture overview

The current implementation is a modular monolith: Next.js web/admin clients and Flutter mobile call a NestJS API; the API uses Drizzle over PostgreSQL/Supabase and integrates storage, realtime, OTP delivery, carrier APIs and CI/CD. Several worker classes are registered inside the API process rather than as a separate Render worker service.

Architecture observations

  • API module boundaries and shared contracts are present; the README describes a pnpm/Turborepo monorepo and Drizzle/PostgreSQL architecture.
  • Global OutboxModule is imported by AppModule. Its dispatcher polls the shared outbox_events table every second.
  • ShippingCarrierWorker, CarrierTrackingPoller, and AutoCompleteWorker are providers in the API process. ReturnExpirationWorker is registered in ReturnsModule but the P13 worker flag defaults to disabled unless configured.
  • There is no evidence in the inspected source of a separately deployed worker service being required for these classes to start. The actual staging environment flags and replica count remain unverified.

9. State-machine and lifecycle assessment

Order lifecycle (source-described and observed transition methods)

The OrdersService documents the primary path as DRAFT → SUBMITTED → PENDING_CONFIRMATION → ACCEPTED / PARTIALLY_ACCEPTED / REJECTED / CANCELLED, followed by PREPARING → READY → OUT_FOR_DELIVERY → DELIVERED → COMPLETED. Additional driver, payment-pending, delivery exception and return-to-sender states exist in implementation.

Transition groupObserved behaviorAssessment
Checkout submissionCreates parent/suborders and financial breakdown; bank transfer moves to PAYMENT_PENDING; COD defaults to PENDING_CONFIRMATION.Implemented; provider/manual-payment limitations remain.
Merchant decisionAccept, partial accept, reject; optimistic status updates; inventory release/settlement.Implemented with concurrency checks.

Cancellation / exceptionsOptimistic transitions, stock settlement, shipment sync, delivery exception and RTS paths.Implemented; end-to-end carrier/runtime behavior not verified.

Payment lifecycle

Payment state machine includes CREATED, AWAITING_PAYMENT, AWAITING_VERIFICATION, CONFIRMED/CAPTURED, REJECTED, PARTIALLY_REFUNDED and REFUNDED. The current provider registry has only the manual verification provider. Refund approval updates records and payment state; it does not move money through an external gateway.

Return lifecycle

ReturnsService implements REQUESTED → MERCHANT_APPROVED → BUYER_SHIPPED → RECEIVED → INSPECTED → REFUND_PENDING → REFUNDED, with rejection, cancellation, expiration and escalation paths. Authorization is checked per transition. Expiration/escalation depends on ReturnExpirationWorker activation.

11. Security and tenant isolation

P0 — cross-tenant offer and sales analytics read

Source evidence: catalog.offer.controller.ts class-level guard is only JwtAuthGuard. The merchant offer list, analytics and trend routes accept storeId from query parameters and call services without a caller/organization context. The service filters by the supplied store ID and aggregates order_items by offer.

Impact: an authenticated user may be able to read another merchant's draft/proposed/active offers, pricing terms and sales analytics (order counts, units, revenue). The list service returns all offers for that store, not only public active offers.

What this proves: source path lacks route-level tenant authorization and the service trusts the supplied store ID. What it does not prove: a live unauthorized request has not been executed. The issue is sufficiently clear in source to block launch until corrected and covered by HTTP integration tests.

Evidence and expected remediation
  • Controller: read routes and class-level guard.
  • Service: storeId-only list and analytics query.
  • Existing tenant-scope helpers.
  • Require an authenticated merchant caller context; assert store membership/ownership for merchant endpoints; separate public buyer offer reads from merchant management reads; add cross-tenant HTTP integration tests for list, analytics and trend; verify 403/404 for foreign store IDs.

Other security observations

  • RLS is disabled on all 114 public tables; no public-schema RLS policies exist.
  • Broad TRUNCATE/REFERENCES/TRIGGER grants to anon/authenticated are present. No CRUD table grants were observed in the same grant inventory. Direct exploitability through PostgREST was not demonstrated.
  • PermissionsGuard is explicitly applied on selected controller methods; @RequirePermission metadata alone does not enforce permissions unless a guard runs.
  • OTP source includes fail-closed provider selection and log-redaction tests. The earlier Render plaintext OTP log finding still needs post-fix runtime-log verification.
  • A tracked JWT-shaped artifact in test-token.txt is duplicated in the tracked scratch snapshot. Its current validity/expiry was not verified. Treat its identity/organization claims as sensitive and confirm test-only provenance before removing it from repository history.
  • Carrier credentials are encrypted in source with AES-256-GCM; webhook security, SSRF protection, retry and circuit-breaker code exist. Live provider configuration is NOT VERIFIED.
  • Storage bucket/object access policies and cross-tenant file retrieval were not runtime verified.

12. UX, admin and mobile assessment

Buyer web

  • Search supports active offer counts and lowest-offer price display. For products with an owning store, the direct Add to Cart handler sends product store ID and no offer ID. This can add the owning store's offer while displaying another merchant's lowest price.
  • Product detail pages provide offer comparison and an explicit offerId add path.
  • Cart displays supplier grouping and handles currency context; checkout does not preserve that mixed-currency presentation.
  • Web checkout supports a per-store shipping selection and explicitly labels total as estimated, noting that VAT and delivery are added per supplier. Mixed-currency cart still incorrectly sums unlike minor-unit values and formats the undefined currency as SAR.
  • Digital payment is visibly disabled in the UI, which is consistent with the absence of a digital provider; however, the API still accepts DIGITAL in its allowed-method list.

Admin

  • ManagementPage includes URL-backed search, advanced filters, sorting/pagination, detail dialog, delete actions for configured entities, and product moderation actions. It uses permission hooks.
  • Catalog Import Center is a specialized flow with upload, validation, preview, overrides, execute, errors, retry, report download and export; controller is guarded by JwtAuthGuard, PermissionsGuard and RolesGuard.
  • Payment admin endpoints have explicit permissions for verification, refund approval and settlement operations.
  • Not every API capability has been confirmed to have a dedicated, complete admin workflow. Full runtime admin walkthrough is NOT VERIFIED.

Mobile parity

  • Mobile has buyer product detail offer comparison and merchant offer list/create/detail screens. Merchant offers are not merely a database/API-only feature.
  • Mobile checkout sends fulfillmentMethod but no shippingSelections; backend fans one global fulfillment choice out to every store. Web can select shipping separately per supplier.
  • Mobile checkout does not send a payment method; backend defaults to CASH_ON_DELIVERY. Web offers COD, bank transfer and voucher.
  • Mobile review text says delivery and tax are calculated/invoiced by suppliers on delivery, while the backend default VAT is 15% and is included in checkout financial totals. The buyer is not shown a matching tax calculation before submission.
  • Mobile cart explicitly documents that the API has no remove-promo route; applied promo cannot be removed from the cart UI.
