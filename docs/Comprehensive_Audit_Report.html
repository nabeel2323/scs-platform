1. Executive Summary

This report presents findings from a comprehensive read-only audit of the Smart Commerce & Supply Platform. The audit covered 4 applications (API, Web, Admin Console, Mobile), 164 declared HTTP endpoints, 47 seeded permission keys (46 at audit time; analytics:track added by GAP-6), and 6 RBAC roles. All findings are verified against live source code.

Remediation Status (2026-09-18)

Phase 1 (GAP-1, GAP-2/3, GAP-5) and Phase 2 (GAP-9, GAP-10, GAP-4, GAP-6) are Implemented — 8 of 10 gaps closed. All changes are additive/tightening and typecheck clean (tsc --noEmit for api, web, admin; dart analyze for the mobile router). Phase 3 (GAP-7 Driver role, GAP-8 unused-key cleanup) remains Open. Seed changes (GAP-4, GAP-6) require pnpm --filter @scs/api db:seed + user re-login to take effect at runtime.

TAIF B2 Test Store: PENDING/DRAFT Clarification

The store you observed with status PENDING and verification DRAFT does not prove a verification request was submitted. Two separate entities exist:

  • Store: Created with status: 'DRAFT' and verificationStatus: 'PENDING' by merchant.service.ts:66-92
  • Verification Request: Created separately by POST /v1/stores/:storeId/verify (merchant.service.ts:348-383)

The staging script bootstrap-staging-store.ts creates the store but does not submit verification. The Admin /merchants page shows the store directory, not the verification queue. To verify a store, navigate to /verification and look for a SUBMITTED request.

7. Workflow Analysis

7.1 Merchant Verification Flow

  1. Store creation: POST /v1/stores → DRAFT/PENDING store (merchant.service.ts:66-92)
  2. Document registration: POST /v1/documents → metadata + storage key (merchant.service.ts:286-304)
  3. Submission: POST /v1/stores/:storeId/verify → SUBMITTED request, store PENDING (merchant.service.ts:348-383)
  4. Queue: GET /v1/verification/queue → verificationRequests joined to stores/orgs (merchant.service.ts:386-424)
  5. Detail: GET /v1/verification/:id → request + store + documents (verification/[id]/page.tsx:45-61)
  6. Decision: POST /v1/verification/:id/review → APPROVED/REJECTED/REVISION (merchant.service.ts:435-490)
Workflow Gap — Resolved (GAP-9)

The Admin /merchants page now includes an Actions column: PENDING stores show a "Review" button and other stores a "View" link, both navigating to /verification?store=<id>. Users no longer need to navigate to /verification separately.

7.2 Order FSM

8. Positive Controls

These source-level controls were verified and should be retained:

  • Server-derived buyer identity at checkout (not client-entered)
  • Server-side cart pricing rather than trusting client-entered prices
  • Cart-item ownership checks
  • Target-organization membership check on store creation
  • Explicit permission decorators and guard checks on 75 endpoints
  • Caller-context propagation through inventory and order controllers
  • JWT denylist checks and organization-switch token replacement
  • Hashed refresh-token lookup and rotation
  • User-scoped session/device revocation predicates
  • Order status-history and outbox persistence
  • Explicit request/store/organization verification updates
  • Transaction/rollback handling and certificate verification in staging scripts

9. Coverage Limitations

The following prevent a comprehensive assurance claim:

  • Not every discovered page/screen was fully read through every action and error branch
  • Complete mobile catalog/store/organization-detail behavior remains only partially traced
  • All contract definitions were read, but every controller's runtime schema enforcement was not reconciled
  • Most migration SQL bodies and deployed database constraints were not independently validated
  • Full role-delegation, cross-tenant, suspended-user, device-trust, and realtime policy validation is unfinished
  • Buyer address/profile, review/dispute follow-through, notification preferences, and mobile parity are not exhaustively certified
  • Accessibility, keyboard navigation, responsive layouts, screen-reader behavior, and visual hierarchy were not tested in a browser/device
  • Actual deployed grants, request records, object storage, provider configuration, and external delivery are unknown
  • No complete HTTP/database/browser end-to-end suite was executed
Evidence Levels

Discovered: Route/page/screen exists. Source-traced: UI action → client request → controller → service → persistence/event path examined. Contract-checked: Request, response, identifiers, states, permissions, and error handling reconciled. Test-supported: Relevant positive and negative assertions inspected. Runtime-verified: Authorized isolated execution recorded (none in this audit). Not assessed: Insufficient evidence. N/A: Outside the intended application/role surface.

10. Recommendations

  1. Implemented Mobile role gate (GAP-1, P1) — extend router.dart redirect: read role from the profile provider and redirect non-merchant roles away from /merchant/* (to /home) and hide /driver until Phase 2. Data already available in UserProfile.role.
  2. Implemented Perms-aware web gate (GAP-2/3, P1/P2) — replace/augment hasMerchantAccess() with a hasPerm('merchant:stores:write') check inside store-settings and organization pages, or hide those nav entries for staff (mirroring AdminSidebar.tsx).
  3. Implemented Finish admin page hooks (GAP-5, P2) — wrapped the remaining six pages (users, orders, merchants, verification, kpis, audit) with useRequirePerms + AccessDenied.
  4. Implemented Add verify action to Merchants page (GAP-9, P2) — added an "Actions" column to merchants/page.tsx: PENDING stores get a "Review" button, others a "View" link, both to /verification?store=<id>.
  5. Implemented Add document download to verification detail (GAP-10, P2) — added a "Download" button per document row in verification/[id]/page.tsx calling presignDocumentDownload() (admin lib/api.ts, via authFetch, POST /v1/documents/:id/presign → downloadUrl). The presign endpoint's @RequirePermission was changed from merchant:stores:write to merchant:verification:review.
  6. Implemented Align MODERATOR product curation (GAP-4, P2) — granted MODERATOR admin:merchants:read (view-only) in seed.ts; requires seed re-run + re-login.
  7. Open Define driver role (GAP-7, P3) — add DRIVER role to seed with appropriate permissions; implement backend endpoints for driver workflows.
  8. Open Clean up unused permission keys (GAP-8, P3) — document which of the 23 unused keys are planned for future phases and which should be removed from seed.
