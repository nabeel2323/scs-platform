1.Executive Summary

The SCS platform today is a verified multi-merchant B2B wholesale marketplace core: identity and access control, organizations, a deep catalog (taxonomy, canonical products, merchant offers), quantity-tier pricing, search, a multi-supplier cart, a 16-state order lifecycle with master/sub-order splitting, inventory with reservation semantics, promotions, reviews and disputes, notifications, analytics and audit — plus a substantial shipping and delivery backbone (shipping methods and zones, Aramex carrier integration, delivery exceptions, retries, cancellation, and return-to-sender workflow) delivered through the M7.2/M7.3 milestone series.

Engineering quality is high where milestones have formally closed: every milestone from M7.2.1 through M7.3-B.5 carries a four-gate evidence chain (architecture audit → decision lock → implementation → independent runtime verification against a real database). 1,634 regression tests plus PostgreSQL integration suites pass; concurrency and tenant-isolation properties are verified at runtime, not assumed.

Measured as a complete B2B framework, three structural deficits stand out

1. A financial void. There is no payments capability at all — the payments module is an empty directory, no provider integration, no refunds, no invoices, no credit accounts. Checkout today is effectively offline/cash-on-delivery. The authoritative plan assigns this to Phase 3, which has not started.

2. Shipping operations are invisible to humans. The entire, fully-verified shipping-operations backend — shipment creation/cancellation/labels, delivery-exception handling and retries, the complete return-to-sender (RTS) workflow, carrier credentials and the carrier recovery queue — has no user interface anywhere. Operations staff cannot run delivery operations without calling the API directly.

3. Classic B2B procurement capabilities are absent. No request-for-quotation (RFQ) workflows, no order approvals or spending limits, no customer-specific price resolution (database columns exist but are unused), no buyer address book, no post-delivery returns (audited, not yet built), no email channel, and an English-only interface despite Arabic support in backend search.

Verdict

The platform is a strong transactional marketplace foundation with verified integrity — but it is not yet a complete B2B framework. The next coherent steps are: (a) expose the already-built shipping/RTS operations through user interfaces, (b) close the returns loop, (c) build the financial layer (payments → refunds → reconciliation), then (d) decide which classic B2B procurement capabilities (RFQ, contract pricing, credit) are in scope.

4.What Is Strong Today

These capabilities are complete and user-facing — the workflow runs end-to-end from screen to database and back, with tests behind it.

Identity & access

Dual login (one-time-code + password), token rotation with theft remediation, device trust, session management, organization switching — across all three apps.

Organizations & roles

Organization CRUD, member management, update-request review, invite codes, role/permission model with verified tenant isolation.

Catalog depth

Categories, brands, attributes and product types (with a visual schema builder and conditional rules), products and variants, media pipeline, canonical product deduplication (GTIN/EAN/MPN), moderation, data-quality dashboards.

Merchant offers

Full offer lifecycle (draft → proposed → active, approve/reject/suspend), offer comparison for buyers, immutable price snapshots at checkout.

Search & discovery

Full-text search with typo tolerance and Arabic normalization, dynamic attribute-driven filters, price/brand/category facets, product comparison, shareable URLs.

Cart & ordering

Multi-supplier cart, idempotent checkout (no duplicate orders), master order split into per-store sub-orders, 16-state order lifecycle, merchant accept/partial-accept/reject, buyer cancellation and reorder, status timelines everywhere.

Inventory

Store and warehouse stock, adjustments, transfers, bulk updates, automatic reserve-on-accept / release-on-cancel / sale-on-delivery, low-stock alerts, movement ledger with CSV export — concurrency verified under 100-way races.

Pricing & promotions

Price lists with quantity tiers and validity windows, one shared price resolver for product page, cart and checkout (no price disagreements), promotions with checkout redemption.

Import & export

Excel catalog import pipeline (parse → validate → resolve → plan → execute) in both admin and merchant surfaces, template generator, import history, product and inventory CSV exports.

Governance & audit

Merchant verification queue, offer governance, dispute resolution console, KPIs, analytics, a complete audit-log viewer, and an event outbox for integrations.

Delivery backbone (backend)

Aramex carrier integration with webhooks, delivery exceptions with retry, carrier-cancellation reconciliation with recovery queue, and a verified three-state return-to-sender workflow — awaiting its user interface (see next section).

Merchant verification & onboarding

Registration wizard, document upload with secure presigned storage, admin review queue, store/warehouse setup — a complete path from registration to selling.

5.The Three Structural Deficits

Deficit 1 — The financial void BLOCKING

There is no payments capability at all. The payments module is an empty directory. No payment provider, no transaction records, no refunds, no invoices, no credit notes, no payment reconciliation. The order lifecycle’s PAYMENT_PENDING state exists but is unreachable. Checkout completes without money moving; the buyer UI shows an “invoiced on delivery” notice, and delivery/tax amounts are currently defaulted to zero at checkout (a documented backend gap).

Consequence: the platform cannot collect revenue, cannot refund cancelled or returned orders, cannot financially close disputes, and cannot issue the invoices B2B buyers require. The authoritative plan assigns all of this to Phase 3, which has not started; refunds are planned as milestone M7.3-D.

Evidence: apps/api/src/modules/payments/ (empty dir); orders.service.ts (PAYMENT_PENDING unreachable); CAPABILITY-MATRIX.md backend gaps BG-2/BG-3; Smart_Commerce_Development_Implementation_Plan.md Phase 3 (line 1380).

Deficit 2 — Shipping operations are invisible to humans BLOCKING

The M7.2.3/M7.3 series delivered a substantial, runtime-verified shipping-operations backend — and almost none of it can be reached from any screen:

  • ~32 operationally-critical endpoints with zero UI: shipment create/cancel/labels, delivery-exception report and retry (8 canonical exception types), the full RTS workflow (request → approve → reject → complete, plus the LOST direct flow), carrier credentials and configurations, and the carrier recovery queue.
  • Admin console: 38 pages, none for shipments, exceptions, RTS, or carriers. The order detail page is read-only.
  • Merchant web: shipping configuration (methods and zones) exists, but no shipment operations, no exception visibility, no RTS actions.
  • Buyers: see tracking data, but exception and RTS states are not surfaced — a delivery in distress is invisible to both buyer and merchant.
  • Mobile: only a driver shipment list consumes any of this surface.

Consequence: the verified B.5 investment is operationally unrealized — staff would need direct API calls to run delivery operations. This is the cheapest high-value gap to close: the backend contracts are stable and verified; only UI work is required.

Evidence: shipment-operations.controller.ts (10 endpoints), carrier-admin.controller.ts (11 endpoints); no /shipments, /exceptions, /carriers pages in apps/admin or apps/web; grep for rts/exception UI controls returns only buyer tracking and config pages.

Deficit 3 — Classic B2B procurement capabilities are absent PRODUCT DECISIONS REQUIRED

  • No RFQ / quotations — no entity, endpoint, or screen anywhere; also absent from the authoritative plan. Requires a product decision.
  • No order approvals or spending limits for buyer organizations.
  • Customer-specific pricing is dark: price lists carry audience (PUBLIC/SEGMENT/CONTRACT) and segment_id columns since migration 0006, but price resolution never uses them and no buyer-segments table exists — the schema anticipated B2B pricing that was never switched on.
  • No buyer address book — checkout collects a free-text street/city each time; no multi-location delivery for organizational buyers.
  • No post-delivery returns (RMA, inspection, restock) — scoped and audited as M7.3-C, not yet implemented; the inventory ledger’s RETURN movement type sits unused.
  • Communication channels: SMS sending is a code stub (one-time passcodes ride on it — a launch risk), there is no email channel at all, and WhatsApp is a stub channel.
  • English-only interface: both web apps hardcode lang="en" dir="ltr"; Arabic exists only in backend search normalization — a market-fit gap for a Saudi B2B platform.
  • Trade credit / payment terms: intentionally excluded until Phase 7 with regulated partners (documented fence) — not a defect, but stakeholders should know it is not part of the current framework.
Evidence: repository-wide scans for quote/invoice/credit/return entities (zero hits outside prose); price-resolution.ts (no audience filter); notifications.service.ts line 312 (SMS stub); apps/web|admin/src/app/layout.tsx (lang/dir hardcoded); plan lines 1352, 1384 (credit fences).

13.Recommended Roadmap

Nature of this roadmap

Recommendation only — nothing here is implemented by the audit. Every milestone should follow the established four-gate governance pattern: Pre-Implementation Architecture Audit → Business Rules + Architecture Decision Lock → Implementation → Independent Runtime Verification → Release Closure. No UI work package is scheduled before its backend contract is verified-stable.

Roadmap logic

  1. Visibility before new behavior — the B.5-verified shipping/RTS backend is unusable by humans; exposing it (R0) is cheaper and higher-value than any new backend.
  2. Close physical loops before financial loops — returns/restock (R1) complete the goods cycle that refunds (R3) will financially settle.
  3. Payments is the financial root — refunds, invoices, finance console, and dispute closure all depend on it (R2).
  4. Commercial depth after the spine is stable — segment pricing, address book, i18n, reporting (R4) ride on stable order/payment contracts.
  5. Product-gated B2B procurement last — RFQ, approvals, credit require explicit product decisions and, for credit, regulated partners (P7 fence).

17.Strategic Conclusion

25.1 — Current platform state

A release-governed, integrity-verified B2B marketplace core at M7.3-B.5: identity/RBAC/orgs, deep catalog + offers, tier pricing, search, cart, 16-state orders, inventory, promotions, disputes, notifications (in-app/push), analytics/audit, plus a verified shipping/delivery/cancellation/RTS backend — with 1,634+ green tests and runtime-verified concurrency and tenant isolation. HEAD exactly equals the B.5 closure baseline; no post-B.5 code exists.

25.2 — B2B framework completeness

Complete

Identity/auth, org/RBAC, catalog & offers, search, cart, ordering FSM (delivered scope), inventory (delivered scope), promotions, reviews/disputes (create → resolve), import/export, admin governance, auditability.

Partial

Buyer-org UX on web, pricing (segment dark), notifications (channels stubbed), analytics/reporting, admin operations (read-only orders), fulfillment (no pick/pack — out of scope), driver flow (unprovisioned), i18n.

Missing

Payments (BLOCKING), refunds, returns/restock (audited, ready to build), invoices/documents, RFQ/quotations (undocumented), approvals/spend limits (undocumented), credit/AR (documented P7), address book, email channel, Arabic/RTL UI, ship-ops UI (BLOCKING operational gap).

25.3 — API/UI parity

  • Backend ahead (severe): the entire shipping-operations domain (~32 endpoints: shipment ops, exceptions, RTS, carrier admin/recovery) plus conversations/chat and feature flags.
  • UI ahead: none detected — the Phase 5 gate eliminated fake UI and this audit found no contradictions.
  • Fully aligned: catalog, offers, ordering, inventory, pricing (merchant), promotions, disputes, notifications (in-app), admin governance.
  • Misaligned: checkout/payment state (neither side has payments; UI implies offline settlement); segment pricing (schema ↔ behavior); merchant web cancel matrix vs. the B.5 rule change (needs refresh verification).

25.4 — Critical gaps (must solve before scaling)

  1. Ship-ops visibility (G-01..G-03) — operations cannot run.
  2. Payments void (G-04) — no revenue, no refunds, no finance console.
  3. Returns/restock + refunds chain (G-05/G-06, X-3/X-4) — inventory & financial leakage.
  4. Notification deliverability (G-11) — OTP over stubbed SMS is a launch risk.
  5. Frontend test vacuum (G-18) — regression risk compounds as UI grows.

25.5 — Recommended roadmap horizons

  • Immediate (now → +2 milestones): M7.3-B.6 Ship-Ops UI (+ Playwright net, DRIVER decision) → M7.3-C Returns.
  • Near-term: Phase 3 payments (COD + provider), SMS/email wiring, fee/VAT correctness.
  • Medium-term: M7.3-D refunds, M7.3-E dispute closure, M7.3-F notifications, address book, segment pricing, Arabic/RTL, reporting v1.
  • Long-term (product-gated): RFQ/quotations, buyer approvals/spend limits, bulk ordering, credit/AR (P7-regulated), multi-warehouse/branch, B2C (Phase 4), Ads (Phase 5), AI (Phase 6).
