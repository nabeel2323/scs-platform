A. Executive Summary

Marketplace Transaction Layer: PARTIAL

The SCS Platform has a substantially implemented cart-to-order pipeline with multi-merchant support, immutable price snapshots, a 16-status order FSM, stock reservation, financial breakdowns, and tenant isolation. However, payment processing, shipment tracking, RFQ/negotiation, returns/refunds, and marketplace settlement do not exist beyond schema placeholders or permission seeds.

What Exists (Evidence-Based)

  • Cart: Multi-supplier, offer-aware, price snapshotted at add-time, promo codes, batch add, cart validation — SUBSTANTIALLY IMPLEMENTED
  • Checkout → Orders: Master order + per-store sub-orders, idempotency keys, offer snapshots, financial breakdown (VAT/commission/delivery), auto-advance FSM — SUBSTANTIALLY IMPLEMENTED
  • Inventory: Stock tracking, reservations, movements ledger, warehouse transfers, low-stock alerts, CSV export — SUBSTANTIALLY IMPLEMENTED
  • Pricing: Price lists, quantity tiers, offer-aware shared resolver — IMPLEMENTED
  • Promotions: Store-scoped, code-based, redemption tracking, per-user limits — IMPLEMENTED
  • Reviews/Disputes: Schema + basic CRUD services — PARTIAL

What Does NOT Exist

  • Payment: No tables, no service, no gateway abstraction, no webhooks — NOT STARTED
  • Shipment/Tracking: No tables, no service — NOT STARTED
  • RFQ/Quotation/Negotiation: Zero code anywhere in the repository — NOT STARTED
  • Returns/Refunds: No tables, no service (disputes exist but are not returns) — NOT STARTED
  • Marketplace Settlement/Payout: Commission computed at checkout but no settlement cycle, no merchant payout — NOT STARTED
  • Invoice: No invoice tables or generation — NOT STARTED

Estimated Transaction Lifecycle Completion

Based on the 13-stage lifecycle (Catalog → Discovery → Offer Selection → Cart → RFQ → Checkout → Order → Fulfillment → Shipment → Invoice → Payment → Delivery → Returns), approximately 35–40% of the transactional lifecycle is implemented with repository evidence.

E. Cart Architecture

Cart Ownership

  • One active cart per user_id (not per org — buyer-level)
  • carts.status: ACTIVE → CONVERTED (on checkout)
  • Cart items grouped by store_id for multi-supplier support

Cart Lines

  • cart_items reference: variant, store, quantity, price snapshot (price_minor), tier, offer_id
  • Price is SNAPSHOT at add time — never taken from client, resolved server-side via resolveOfferPrices()
  • Offer selection: buyer can pick a specific merchant offer; line is keyed by (variantId, offerId)
  • Canonical products without store require explicit offer selection

Multi-Merchant Cart

  • Supported — items from different stores coexist in one cart
  • Checkout splits into per-store sub-orders automatically
  • Promotions are store-scoped — applied only to the matching supplier's sub-order

Cart Validation

  • POST /cart/validate — re-checks offer status, re-prices stale items, reports valid/repriced/stale
  • Used before checkout to ensure offer liveness

Security

  • Client-supplied storeId is never trusted — authoritative store derived from variant's product or selected offer
  • Price is never client-supplied — resolved from store's active price lists server-side
  • Offer must be ACTIVE and match variant/product scope

F. Order Architecture & FSM

Order Model

  • Master Order: buyer's purchase intent (one per checkout), has idempotency key
  • Sub-Orders: one per store/supplier, with full financials (subtotal, discount, tax, delivery, total)
  • Order Items: line items with SNAPSHOT prices, SKU/title snapshot, offer_id, offer_snapshot JSONB
  • Financial Breakdown: per sub-order — products, discount, delivery, tax, commission, merchant net
  • Status History: append-only audit trail of every transition
  • Currency: per sub-order (supplier's currency snapshot at checkout)

Order FSM — 16 Canonical Statuses

DRAFT → SUBMITTED → PENDING_CONFIRMATION → ACCEPTED ──────→ PREPARING → READY → OUT_FOR_DELIVERY → DELIVERED → COMPLETED → PARTIALLY_ACCEPTED ↗ → DISPUTED → REJECTED → CANCELLED (from any pre-DELIVERED state) PAYMENT_PENDING → PREPARING | CANCELLED (P3 future) ASSIGNED → PICKED_UP → OUT_FOR_DELIVERY (P2 driver) DISPUTED ≤72h from DELIVERED or COMPLETED

Transition Enforcement

  • Enforced at service layer via TRANSITIONS static map + assertTransition()
  • Invalid transitions throw ConflictException
  • Every transition records in order_status_history and publishes outbox event
  • Auto-advance: SUBMITTED → PENDING_CONFIRMATION after checkout (merchant notification + 15-min SLA)

Stock Lifecycle

  • Reservation: on merchant ACCEPT (not at cart/checkout)
  • Release: on CANCELLED or REJECTED
  • Consumption: on DELIVERED (qty_on_hand and qty_reserved both decrease)
  • All movements recorded in stock_movements ledger with reference to order
  • Replay-safe: net-outstanding calculation prevents double-release

Re-Price Guard (Merchant Accept)

When a merchant accepts an order, checkPriceDeltas() compares current price tiers against the snapshotted unit price. If any line changed by >5%, a 409 Conflict is thrown with per-line deltas — preventing the merchant from accepting at a stale price.

H. Inventory Audit

Inventory Model

  • inventory_items: one row per (variant, warehouse) combination
  • qty_on_hand, qty_reserved, reorder_point, max_stock
  • qty_available = on_hand − reserved (computed, not stored)
  • Inventory belongs to variant + warehouse, not to canonical product or offer directly
  • Offers reference a warehouse via merchant_offers.warehouse_id (optional)

Stock Movements Ledger

Movement TypeEffectSigned Quantity
IMPORTAdds to on_handPositive
ADJUSTAdjusts on_handSigned (+/−)
RESERVEIncreases qty_reservedNegative (reduces available)
RELEASEDecreases qty_reservedPositive
SALEDecreases both on_hand and reservedNegative

Race Condition Analysis

  • reserveStock() uses sql`qty_reserved + ${qty}` — atomic SQL increment, not read-modify-write
  • Available check: qtyOnHand - qtyReserved < input.quantity → throws if insufficient
  • Risk: Two concurrent reservations could both read the same available quantity and both succeed. The SQL increment is atomic, but the availability check is a separate read. A SELECT ... FOR UPDATE or advisory lock would eliminate this race.
  • Current mitigation: the order accept path reserves sequentially per item, reducing (not eliminating) the window.

Multi-Merchant Inventory

  • Each merchant's warehouse holds independent inventory for the same variant
  • Offer → warehouse → inventory_items chain means Merchant A and Merchant B have separate stock pools for the same canonical variant
  • This is correct for the marketplace model

I. Pricing & Promotions

Pricing Architecture

  • price_lists: group pricing rules by store/channel/audience (B2B, PUBLIC, segment-specific)
  • price_tiers: quantity-based tiers per variant per price list (min_qty, max_qty, unit_price_minor)
  • resolveOfferPrices(): shared resolver — highest-priority list, best tier for quantity. Used by both cart and product detail (A5-1 consistency guarantee)
  • Offer-aware: when merchant offers exist, the resolver routes through the offer's price list

Promotions

  • Store-scoped with scope variants: STORE, CATEGORY, PRODUCT, VARIANT
  • Promo types: percentage, fixed amount
  • Redemption tracking with per-user limits
  • Time-bounded (starts_at, ends_at)
  • Applied at checkout per sub-order (store-scoped — never cross-store)

Order Financial Calculations

  • Pure function computeOrderFinancials() — no DB, no side effects, unit-testable
  • VAT: 15% (KSA), applied to taxable base = (goods − discount) + delivery fee
  • Commission: 5% placeholder on net goods (merchant revenue basis)
  • Delivery fee: configurable flat, waived (0) for pilot
  • All amounts in integer minor units — no floats

Idempotency

  • Checkout accepts idempotencyKey — stored on master_orders.idempotency_key (unique)
  • Replay returns existing master order instead of creating duplicate
  • Gap: Cart add/update/delete have no idempotency — safe for UI but not for API retry

Replay Attack Surface

  • Checkout: protected by idempotency key
  • Order status transitions: FSM prevents invalid replays (e.g., ACCEPTED → ACCEPTED not allowed)
  • Cart operations: no idempotency but low risk (add is additive, delete is idempotent)

Open Security Items

  • Cart endpoints lack explicit @RequirePermission — rely on JWT subject only. Low risk since cart is buyer-owned, but inconsistent with the orders pattern.
  • No payment webhook security — no payment system exists yet, so this is a design-time concern for Phase 8.
  • Stock reservation race condition — concurrent reservations could oversell (see Inventory section).

R. Production Risk Assessment

Risk CategoryLevelEvidence
Security RiskMEDIUMTenant isolation is strong (assert helpers on all write endpoints). Price manipulation prevented. But cart lacks explicit permission guards, and no payment webhook security exists (no payment system yet). No IDOR risk on existing endpoints.
Data Integrity RiskMEDIUMPrice snapshots are immutable. Offer snapshots captured at checkout. Financial breakdown written atomically. But stock reservation has a race condition (no SELECT FOR UPDATE), and checkout + reservation are not in a single transaction.
Financial RiskHIGHNo payment processing exists. Orders complete without money changing hands. Commission is computed but never collected. This is the single largest gap — the platform cannot operate as a marketplace without it.
Multi-Tenant RiskLOWTenant isolation verified E2E (Scenario K). assertOrderAccessible, assertStoreInOrg, assertWarehouseInOrg all fail-closed. BYPASS_ROLES only for SUPER_ADMIN/ADMIN/MODERATOR. Sub-order per store ensures merchant isolation.
Operational RiskMEDIUMOutbox events provide reliable async processing. Audit logs capture all write operations. But no shipment tracking means delivery is a black box. No monitoring/alerting for failed payments (no payment system).
Performance RiskLOWCart loading is a single query with joins. Offer comparison uses indexed FTS. Checkout is O(stores × items). No N+1 patterns observed. Stock reservation uses atomic SQL increments. Potential risk at very high concurrency (see data integrity).
Mobile RiskMEDIUM40 Dart screens exist with API integration, but cannot be validated (no Dart SDK). Cart, checkout, orders, merchant screens all present. Driver dashboard is scaffold only.
Testing RiskHIGHCart, checkout, order FSM, inventory, and stock reservation have NO integration or E2E tests. The most critical business flows rely on unit tests only. A regression in checkout could silently break ordering.
