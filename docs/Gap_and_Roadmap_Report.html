1. Executive Summary

The platform is a B2B-first marketplace delivered as a modular monolith with four client surfaces. It is pilot-ready for Phase 1: all three critical launch blockers were resolved and verified on 2026-09-04, and on 2026-09-08 the full P1 + P2 backlog closed — checkout pricing (API-B4), merchant-write RBAC (API-B6), the identity N+1 / prod-JWT-gate / switch-org revocation / auth-DTO hardening (API-B7–B10), admin /v1/me hydration (ADM-B2), the shared @scs/contracts package, realtime wiring and typed mobile models. The remaining Phase 1 gaps are deeper automated test coverage, k6 load-test evidence and a few Low-severity UI items. Phases 2–7 are forward-declared — schema and FSM states exist, behaviour is dark.

5. Blockers & High-Priority Issues

5.1 Critical blockers — all resolved

3 / 3 resolved & verified 2026-09-04

Device-trust bootstrap (API-B1), CORS X-Device-Id (API-B2), and the stubbed CSV/Excel import (API-B3) are fixed and verified end-to-end. Typed auth errors (API-B5) and the daily backup + restore drill also landed the same day. No critical blocker prevents a pilot launch.

5.2 High-priority issues — both resolved 2026-09-08

API-B4 · Resolved 09-08 Checkout pricing computed

Before the 09-08 fix, orders.service.ts hardcoded discount, delivery fee and tax to zero, so the total equalled the sum of the line subtotals:

const discount = 0;   // TODO: apply promotion
const deliveryFee = 0; // TODO: calculate fee
const tax = 0;         // TODO: calculate VAT (15%)
const total = subtotal - discount + deliveryFee + tax;

Impact (was): promo codes stored but never discounted; KSA 15% VAT never charged; delivery fees never collected — blocked the “end-to-end transaction” readiness criterion and real revenue accounting.

Fix: orders.service.ts now prices percent/fixed/qty promotions, adds 15% VAT and the delivery fee, and persists an order_financial_breakdown per order (covered by order-pricing.spec.ts + orders.service.spec.ts).

API-B6 · Resolved 09-08 Merchant-write RBAC enforced

All 19 @RequirePermission decorators sit on admin, verification-review and brand-management endpoints:

admin.controller.ts15 × admin:*
merchant.controller.ts3 × merchant:verification:review
catalog.controller.ts1 × catalog:brands:manage

Impact (was): merchant product / order / promotion / inventory write endpoints relied on the JWT guard + ownership checks alone, with no fine-grained permission gate.

Fix: @RequirePermission now guards merchant/catalog writes, backed by seeded merchant:products:write, merchant:orders:write and merchant:promotions:write keys (a MODERATOR can no longer mutate merchant catalog; covered by merchant-rbac.spec.ts).

Sequencing note

API-B4 landed before API-B6 as planned: pricing correctness (a launch-readiness criterion) first, then RBAC hardening for scale. Both are now closed, so no high-priority backend issue remains open for pilot GA.

9. Enhancement Recommendations

Landed 09-08 + 09-14

Most of these are now implemented: N+1 claim building, single-flight refresh and Socket.IO push (Performance); merchant/catalog RBAC, prod JWT gate and auth DTOs (Security); CI pipeline, @scs/contracts and identity/orders coverage gates (DX); remaining-attempts lockout UX (UX); S3 storage integration with bucket validation, presigned PUT URLs and 15-min expiry caps (09-14). Still open: Redis category caching, pagination-default enforcement, FCM lockout notifications, pen test, and the offline/queue/replica scalability notes.

Performance

  • Fix N+1 in claim building with a single join; target <5 queries per refresh.
  • Cache categories/brands in Redis (60s TTL) — they front every search page.
  • Refresh-token rotation concurrency guard (single in-flight promise).
  • Adopt the Socket.IO gateway for order-status push; retire polling gaps.
  • Enforce pagination defaults (limit ≤ 50) server-side on all list endpoints.

Security

  • Extend @RequirePermission to merchant/catalog writes + seed the keys.
  • Production config gate: fail fast if JWT_ACCESS_SECRET is unset outside dev.
  • DTOs for all auth bodies so forbidNonWhitelisted actually filters.
  • Account-lockout notification via the existing FCM channel on rate-limit trips.
  • External pen test before Phase 3 payments go live.
  • Storage bucket allow-list + 15-min presigned-URL cap Done 09-14.

Developer experience

  • CI: typecheck + lint + dart analyze + migration dry-run on every PR.
  • Shared @scs/contracts (OpenAPI to TS + Dart codegen) to stop client drift.
  • Coverage gates on identity/orders; widget + Playwright smoke tests.
  • Seed script inserts admin:* keys + a demo password-credential user.

User experience

  • RFC 7807-aware error surfaces (map type to a localized message) on all clients.
  • “Forgot password” to OTP-reset flow (OTP is already authoritative).
  • Remaining-attempts UX on lockout (read X-RateLimit-Remaining).
  • Order-gated review/dispute pickers (remove manual UUID entry).
  • Skeleton loaders on web (mobile already has shimmer).

Scalability

  • Keep the modular monolith through pilot; first extraction candidate = notifications.
  • Move import processing to a BullMQ queue on existing Redis.
  • Introduce read replicas only after Phase 3 volume; measure buildClaims first.
  • Define module-boundary lint rules (the monorepo already documents enforcement).
