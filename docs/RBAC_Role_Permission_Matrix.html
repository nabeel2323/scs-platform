1. Executive Summary

Every authenticated action in the platform is authorized through a single chain: a JWT perms claim minted per active organization role, enforced server-side by PermissionsGuard, and mirrored client-side where each surface consumes role/permission data returned by GET /v1/me. The seed defines 46 permission keys across 6 roles; 73 of ~120 endpoints carry an explicit @RequirePermission key, with the remainder self-scoped (a user may only read/modify their own resources).

1.2 App Separation & Role Boundaries

The platform has 3 separate applications, each serving distinct user groups. Roles do not span all apps — each role uses only the app(s) designed for their workflow:

ApplicationPathWho Uses ItPurpose
Admin Console apps/admin SUPER_ADMIN, ADMIN, MODERATOR Platform oversight: manage users, merchants, verification requests, categories, orders, KPIs, audit logs, disputes
Web App apps/web BUYER, MERCHANT_OWNER, MERCHANT_STAFF Buyer flows (search, cart, checkout, orders) and merchant flows (store management, catalog, pricing, inventory, promotions)
Mobile App mobile/ BUYER, MERCHANT_OWNER, MERCHANT_STAFF Same as Web App but mobile-optimized
Key Insight

SUPER_ADMIN, ADMIN, and MODERATOR only use the Admin Console — they never access buyer or merchant flows. BUYER only uses Web App and Mobile — they never access the Admin Console. MERCHANT_OWNER and MERCHANT_STAFF use Web App (merchant segment) and Mobile — they never access the Admin Console.

This means when analyzing UI gaps, you must check the correct app for each role. For example:

  • SUPER_ADMIN verifying merchants → check Admin Console /verification pages
  • ADMIN managing categories → check Admin Console /categories page
  • MERCHANT_STAFF updating store settings → check Web App /merchant/store page
  • BUYER browsing products → check Web App /search or Mobile home screen
Verified Findings

The earlier audit gaps (GAP-1..GAP-10) are confirmed closed in live source: inventory (8), pricing (10), analytics reads (2), organization writes (4), order checkout/reorder/cancel (3), dispute resolve/response (2) and document presign endpoints all carry explicit guards. Client-side gating exists in Web (merchant/layout.tsx, Navbar.tsx) and Admin (AdminSidebar.tsx, useRequirePerms), and /v1/me returns the perms array (GAP-6). Remaining gaps are documented in section 11.

2. RBAC Architecture

2.1 Authorization Chain

  1. Role assignment — each user holds organization_members rows linking them to an org + role. The active membership determines authorization context.
  2. Claims resolution — IdentityService.buildClaims() (identity.service.ts:1055-1071) resolves rolePermissions for the active roleId, batch-fetches permission keys, and returns { activeOrgId, roleKey, permissions }.
  3. JWT minting — access tokens carry sub, activeOrg, role, perms, sid, jti (current-user.decorator.ts:JwtPayload). Refresh, password login and switch-org all re-mint with fresh claims; the old token's jti is denylisted in Redis on switch, closing the stale-permission window.
  4. Server enforcement — PermissionsGuard (permissions.guard.ts) reads PERMISSIONS_KEY metadata set by @RequirePermission(...) and requires every listed key to be present in request.user.perms; failures return 403 with an RFC 7807 body (https://errors.scs.local/forbidden).
  5. Client mirroring — GET /v1/me re-resolves the same permission set (identity.service.ts:334-348, audit GAP-6) so clients gate UI from the identical source of truth. Web hydrates AuthUser.perms after every token mint; Admin stores AdminUser.perms.

5. Role Profiles & Accessible Endpoints

5.1 SUPER_ADMIN — 46 keys (all permissions)

Capabilities: every platform operation including user/role management, organization writes, merchant verification, product moderation, KPIs and audit access. Only role that holds identity:users:delete, identity:roles:write, catalog:brands:manage and the ads:* trio (reserved).

Endpoints: all 120+ API routes; every guarded endpoint passes. Surfaces: full Admin Console (all 11 sidebar items visible).

Source: seed.ts:88-91 (grants PERMISSIONS wholesale).

Capabilities: platform operations without destructive identity powers — merchant verification approve/reject, user read/write (no delete), order oversight with cancel/refund, inventory + pricing oversight (RBAC audit), full admin ops (admin:*), payments read/refund, analytics and audit reads, dispute resolution.

5.3 MODERATOR — 14 keys

Capabilities: curates the platform catalog (product/category CRUD incl. merchant:products:write so guarded catalog writes pass), reviews merchant verifications, reads inventory/pricing, responds to disputes. Cannot manage users, view KPIs or audit logs (sidebar hides these).

Mismatch Watch

MODERATOR holds merchant:products:write but not admin:merchants:read, so the Admin Products moderation page (requires admin:merchants:read) is hidden and its API returns 403. Product curation happens through catalog write endpoints instead. See GAP-4.

Capabilities: full store lifecycle (create/update store, warehouses, documents + presign upload, verification submission), product/variant/media/import management, merchant order actions (accept/partial/reject/confirm/transition), promotions, inventory and pricing management, organization writes (add/remove members).

5.5 MERCHANT_STAFF — 13 keys

Capabilities: day-to-day store operations — identical to owner for products, orders, promotions, inventory and pricing. Cannot create/update stores or warehouses (merchant:stores:write is owner-only), cannot write organizations. Count is contract-asserted at exactly 13 by bootstrap-staging-staff.ts:137 (staging user +966500000011).

UI/API Mismatch

The Web merchant gate checks role (MERCHANT_OWNER | MERCHANT_STAFF), so staff can open /merchant/store and /merchant/organization pages, but every write action there returns 403 because staff lack merchant:stores:write / identity:organizations:write. See GAP-2.

5.6 BUYER — 5 keys

Capabilities: browse verified stores, search/view catalog, cart + checkout (orders:write), order history (orders:read), cancel eligible orders (orders:cancel). Reviews, disputes, favorites, saved suppliers, profile/credentials and notifications are self-scoped routes guarded only by JwtAuthGuard — any authenticated user (including buyers) passes, with row-level ownership enforced in services.

5.7 Driver — not in RBAC (Phase 2)

No DRIVER role, permission keys or org-membership model exists in the seed. The mobile /driver route renders a UI scaffold with hardcoded data (driver_dashboard_screen.dart); the Accept button is a no-op. Any authenticated mobile user can currently navigate there because mobile has no role gating (GAP-1). Driver RBAC is a Phase 2 deliverable.

7. UI Consistency — Web App (apps/web)

7.1 Navigation Gating

Navbar.tsx (apps/web/src/components/Navbar.tsx:17,68-72) derives isMerchant from isMerchantRole(user?.role) — reactive to login/logout via useAuth() — and renders the Merchant link only for MERCHANT_OWNER/MERCHANT_STAFF. Buyer links (Search, Stores, Favorites, Suppliers, Cart, Orders, Notifications) are always visible; Sign In/Account switch on authentication state.

7.2 Route-Group Gate

apps/web/src/app/merchant/layout.tsx is a client layout covering the entire /merchant/* segment. For each navigation it (1) exempts open paths, (2) requires isAuthenticated() else redirects to /auth/login, (3) requires hasMerchantAccess() else redirects buyers to /search. It renders nothing until checks pass, preventing flash-of-forbidden-content.

7.3 Page-Level Checks

  • Hydration — lib/auth.ts:hydrateUserFromProfile() refreshes role+perms from /v1/me after OTP verify, password login and switchOrg, so gating matches the server after org switches (audit A2-2).
  • Admin links — hasAdminAccess() exists in lib/auth.ts:177-180 but no web route group currently consumes it (web has no admin pages; admins use the Admin Console).
  • Perms underuse — web checks role, not the perms array, for merchant gating; feature-level permission awareness is not implemented client-side (GAP-3).

9. UI Consistency — Mobile (mobile/)

9.1 Route Protection

mobile/lib/router/router.dart:36-42 implements a single authentication redirect: unauthenticated users are forced to /login; authenticated users are pushed away from /login to /home. No role-based redirect exists. All 30 routes — buyer, merchant and driver — are reachable by any authenticated token holder.

9.2 Role Data Availability

The mobile model layer already carries role (models.dart:605-628, UserProfile.role from /v1/me) and membership roles per org (models.dart:692 maps roleKey), and screens display role labels (e.g. profile_screen.dart:119). The data needed for gating is present; only the router decision and screen-level conditionals are missing.

12. Recommendations

  1. Mobile role gate (GAP-1) — extend router.dart redirect: read role from the profile provider and redirect non-merchant roles away from /merchant/* (to /home) and hide /driver until Phase 2. Data already available in UserProfile.role.
  2. Perms-aware web gate (GAP-2/3) — replace/augment hasMerchantAccess() with a hasPerm('merchant:stores:write') check inside store-settings and organization pages, or hide those nav entries for staff (mirroring AdminSidebar.tsx).
  3. Finish admin page hooks (GAP-5) — wrap remaining six pages with useRequirePerms; the hook + AccessDenied component already exist, so this is mechanical (e.g. Users: admin:users:read, KPIs: admin:kpis:read, Audit: admin:audit:read).
  4. Align MODERATOR product curation (GAP-4) — either grant moderators admin:merchants:read (view-only) or accept the current catalog-endpoint path and document it in the admin runbook.
  5. Phase 2 driver RBAC — before enabling driver flows: add driver:* keys + role to seed.ts, guard new delivery controllers, and gate the mobile /driver route by role.
  6. Guard-rail test — add a unit test that diffs every @RequirePermission string against the seed PERMISSIONS array (catches the mismatch class documented in section 2.2 before runtime 403s).
