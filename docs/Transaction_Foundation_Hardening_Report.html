4. Inventory Concurrency Solution (P0)

Before

for each item: for each warehouse: read inventory (no lock) open transaction SELECT ... FOR UPDATE check availability reserve commit ← Each item commits separately!

After

open SINGLE transaction for each item: for each warehouse: SELECT ... FOR UPDATE (locked) check availability reserve commit ← All items commit together or all roll back

Locking Strategy

  • Scope: Single transaction wraps ALL item reservations for an order
  • Lock type: SELECT ... FOR UPDATE on each inventory row
  • Granularity: Per-row locking (Offer A inventory doesn't block Offer B)
  • Deadlock risk: Low — items processed in order, locks acquired sequentially
  • Rollback: If any item fails, entire transaction rolls back — no partial reservations

5. Checkout Transaction Boundary

The checkout flow executes within a single database transaction:

  1. Insert master_orders (with idempotency key)
  2. For each store group:
    • Insert orders (sub-order)
    • Insert order_items (with offer snapshot)
    • Insert order_financial_breakdown
    • Insert order_status_history
  3. Update carts status → CONVERTED
  4. Insert outbox_events (transactional outbox)

Atomicity: If any step fails, everything rolls back. No partial orders, no orphan sub-orders, no leaked cart conversions.

Idempotency race protection: If two concurrent requests arrive with the same idempotency key, the unique constraint on master_orders.idempotency_key raises PostgreSQL error 23505. The catch block detects this and returns the existing order instead of failing.

6. Security

Cart Authorization

  • Ownership: All cart operations scoped by userId — no cross-user access
  • Item isolation: updateItem and removeItem verify item.cartId === user's cart.id
  • Price integrity: Prices resolved server-side via resolveOfferPrices() — client cannot supply price
  • Store derivation: storeId derived from product/offer, never trusted from client
  • Offer validation: Offer must be ACTIVE and match variant/product scope

Tenant Isolation

  • Cart scoped to userId — buyers see only their own cart
  • Orders scoped by buyerId or storeId via assertOrderAccessible()
  • Inventory scoped by assertInventoryItemInOrg() — merchants see only their org's inventory
  • Existing E2E Scenario 11 verifies tenant isolation

Price Tampering Protection

  • Cart AddCartItemInput has no priceMinor field — client cannot supply price
  • Checkout re-validates offer status and re-snapshots price
  • Order items store immutable unitPriceMinor and offerSnapshot
  • Historical orders unaffected by subsequent offer price changes

7. Idempotency

Same Key, Same Request

First request creates order. Second request with same key returns existing order (no duplicate).

Concurrent Same Key

Two simultaneous requests with same key: unique constraint on idempotency_key prevents duplicate insert. One succeeds, the other catches error 23505 and returns the existing order.

Conflicting Payload

Same key but different cart: not explicitly validated. The idempotency key is assumed to represent the same logical operation. If the cart changed, the first request's order is returned. This is acceptable — the client should generate a new key for a new operation.

8. Order FSM

16 canonical statuses with transition matrix enforced via assertTransition():

DRAFT → SUBMITTED → PENDING_CONFIRMATION → ACCEPTED | PARTIALLY_ACCEPTED | REJECTED | CANCELLED ACCEPTED/PARTIAL → PREPARING → READY → OUT_FOR_DELIVERY → DELIVERED → COMPLETED Any pre-DELIVERED → CANCELLED DELIVERED/COMPLETED → DISPUTED (≤72h)

Tested transitions: E2E Scenario 5 verifies valid transitions, invalid transitions, and terminal state rejection.

History: Append-only order_status_history records every transition with actor, reason, timestamp.

9. Snapshot Integrity

12. Remaining Risks

P2 — Low Priority

  • Idempotency payload validation: Same key with different cart is not explicitly rejected. Acceptable if clients generate unique keys per operation.
  • Partial reservation policy: If an item has insufficient stock, reserveStock reserves what's available (Math.min(ordered, available)). Merchant can partially fulfill. Document behavior, don't change.

P3 — Future Enhancement

  • Advisory locks for idempotency: Current approach relies on unique constraint + catch. Could use PostgreSQL advisory locks for earlier detection, but current approach is safe and simpler.
  • Batch inventory locking optimization: Current implementation locks rows sequentially. Could sort by inventory item ID to reduce deadlock risk, but risk is already low.
