Phase B — Stock Concurrency Fix

P0 Race Condition: reserveStock() used a read-check-update pattern without row locking. Two concurrent requests could both read available=5, both reserve 5, and oversell 10 units against 5 on-hand.

Fix: SELECT ... FOR UPDATE

Wrapped reserveStock() and releaseStock() in DB transactions with PostgreSQL row-level locking:

async reserveStock(input, caller?) {
  return this.db.db.transaction(async (tx) => {
    const locked = await tx.select({ qtyOnHand, qtyReserved })
      .from(inventoryItems)
      .where(eq(inventoryItems.id, input.inventoryItemId))
      .for('update')          // ← Row-level lock
      .then(rows => rows[0]);

    const available = locked.qtyOnHand - locked.qtyReserved;
    if (available < input.quantity)
      throw new BadRequestException('Insufficient available stock');

    await tx.update(inventoryItems)
      .set({ qtyReserved: sql`qty_reserved + ${input.quantity}` })
      .where(eq(inventoryItems.id, input.inventoryItemId));

    // RESERVE movement written inside same transaction
    await tx.insert(stockMovements).values({ ... });
  });
}
Why FOR UPDATE, not mutex: Application-level mutexes don't work across multiple API replicas. PostgreSQL row locks serialize access at the database level, providing correctness regardless of deployment topology.

Phase C — Cart Security Assessment

Result: Existing user-scoped isolation is adequate. No RBAC changes needed.

Analysis

  • CartController uses JwtAuthGuard — all cart operations scoped to authenticated user
  • Cart queries use userId from the JWT token (@CurrentUser()), never from client input
  • Cart items are scoped to the user's cart via cartId lookups
  • No cross-tenant data leakage possible — each buyer sees only their own cart

Adding explicit RBAC permissions (e.g., cart:write) would be inconsistent with the existing architecture where cart operations are inherently user-scoped. The JwtAuthGuard provides the correct security boundary.

Phase D — Checkout Transaction Boundary

P0 Atomicity Gap: Checkout performed multiple independent DB writes (master order, sub-orders, items, financials, status history, cart conversion) without a transaction envelope. A crash mid-checkout could leave orphaned master orders without items, or items without financial breakdowns.

Fix: Single Transaction Envelope

All checkout writes are now wrapped in a single DB transaction:

await this.db.db.transaction(async (tx) => {
  await tx.insert(masterOrders).values({ ... });
  for (const [storeId, items] of grouped) {
    await tx.insert(orders).values({ ... });
    await tx.insert(orderItems).values({ ... });
    await tx.insert(orderFinancialBreakdown).values({ ... });
    await tx.insert(orderStatusHistory).values({ ... });
  }
  await tx.update(carts).set({ status: 'CONVERTED' });
  await tx.insert(outboxEvents).values({ eventType: 'order.submitted', ... });
});

Design Decisions

  • Read-only operations (store metadata, promotion resolution) moved before the transaction
  • Transactional outbox: Outbox event written via tx.insert(outboxEvents) inside the transaction, not via outbox.publish() which uses a separate connection
  • Post-transaction side effects (promotion redemption, auto-advance, notifications) are best-effort with try/catch
  • Price re-quote guard refactored to use the shared resolveOfferPrices() resolver for consistency with cart pricing (A5-1)

Additional Fix: checkPriceDeltas Consistency

The re-price guard in acceptOrder() previously used a custom SQL query with sql\`min_qty <= quantity\` that returned incorrect results (currentPrice: 0). Refactored to use the shared resolveOfferPrices() resolver, ensuring the guard compares apples-to-apples against the checkout snapshot.
