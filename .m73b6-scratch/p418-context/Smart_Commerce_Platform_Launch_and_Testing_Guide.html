pnpm --filter @scs/api dev:proxy

# Expected output:
# 🔌 PG proxy listening on 127.0.0.1:15432
#    → scs-postgres:5432

# Terminal 2 — NestJS API on port 3000
pnpm --filter @scs/api dev

# Expected output:
# [Nest] NestJS Modular Monolith listening on :3000
# [Nest] RealtimeGateway subscribed to /realtime
# [Nest] OutboxDispatcher polling (interval: 1000ms)
Verify: curl http://localhost:3000/v1/healthz should return {"status":"ok"}
⚠ Windows Docker Desktop: Node.js PostgreSQL clients cannot connect directly to Docker-mapped ports on Windows. The PG proxy (infra/pg-proxy.ts) tunnels connections through docker exec, bridging the protocol correctly. Always start the proxy before the API. The API's DATABASE_URL defaults to port 15432 (the proxy).

9. Integration Verification

End-to-end verification of critical platform flows.

9.1 Auth Flow — Full Cycle

# Step 1: Request OTP (use demo buyer account)
curl -X POST http://localhost:3000/v1/auth/otp/request \
  -H "Content-Type: application/json" \
  -d '{"phone":"+966500000100"}'
# Expected: 201 Created

# Step 2: Verify OTP (check API logs for the code)
curl -X POST http://localhost:3000/v1/auth/otp/verify \
  -H "Content-Type: application/json" \
  -d '{"phone":"+966500000100","code":"<OTP_FROM_LOGS>"}'
# Expected: 200 with { accessToken, refreshToken }

# Step 3: Refresh token
curl -X POST http://localhost:3000/v1/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refreshToken":"<REFRESH_TOKEN>"}'
# Expected: 200 with new accessToken + rotated refreshToken

# Step 4: Verify old refresh token is invalidated (reuse detection)
curl -X POST http://localhost:3000/v1/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refreshToken":"<OLD_REFRESH_TOKEN>"}'
# Expected: 401 — session revoked

9.2 Order Lifecycle — Full FSM

# The 16-status canonical FSM:
# DRAFT → SUBMITTED → PENDING_CONFIRMATION → ACCEPTED → PREPARING
# → READY → ASSIGNED → PICKED_UP → OUT_FOR_DELIVERY → DELIVERED
# → COMPLETED → DISPUTED
# Also: PARTIALLY_ACCEPTED, PAYMENT_PENDING, CANCELLED, REJECTED

# After checkout, verify auto-advance:
# 1. POST /v1/checkout → creates order with SUBMITTED
# 2. System auto-advances to PENDING_CONFIRMATION (merchant notified, SLA started)
# 3. Merchant: POST /v1/orders/:id/accept → ACCEPTED
# 4. Merchant: POST /v1/orders/:id/status → PREPARING
# 5. Merchant: POST /v1/orders/:id/status → READY
# 6. Merchant: POST /v1/orders/:id/status → OUT_FOR_DELIVERY
# 7. Merchant: POST /v1/orders/:id/status → DELIVERED
# 8. Buyer: POST /v1/orders/:id/status → COMPLETED

# Verify each transition:
# - order_status_history has append-only record
# - outbox_events has corresponding domain event
# - Invalid transitions throw 409 Conflict (RFC 7807 format)
FSM backward compat: acceptOrder(), rejectOrder(), and partiallyAcceptOrder() all auto-advance from SUBMITTED → PENDING_CONFIRMATION before processing, so legacy clients still work.
