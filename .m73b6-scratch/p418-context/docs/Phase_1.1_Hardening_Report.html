2. P1.1-A — Idempotency Fingerprint Conflict Detection

2.1 Problem Statement

Phase 1 implemented idempotency via a unique constraint on master_orders.idempotency_key and a catch block for PostgreSQL error 23505. This correctly prevents duplicate orders when the same key is retried.

However, it did not detect when the same key was used for a different logical checkout (e.g., different cart contents). The system would silently return the first order, masking the conflict.

2.2 Solution — Server-Side Fingerprint

A SHA-256 fingerprint of the authoritative checkout intent is computed server-side and stored alongside the idempotency key. On replay, the fingerprint is recomputed and compared. A mismatch returns HTTP 409 Conflict.

Fingerprint Composition

SHA-256( sorted_cart_items + "|" + fulfillmentMethod + "|" + canonical_delivery_address ).slice(0, 64) Where each cart item = "variantId:quantity:offerId" Sorted by "variantId|offerId" for deterministic ordering. Delivery address = JSON.stringify with sorted keys.

Authoritative Fields (server-derived, never client-trusted)

  • variantId — which product variant
  • quantity — how many units
  • offerId — which merchant offer (price source)
  • fulfillmentMethod — PLATFORM_DELIVERY | PICKUP | etc.
  • deliveryAddress — canonical delivery location

Excluded Fields (not in fingerprint)

  • Client-supplied prices, totals, subtotals
  • Timestamps, request metadata, random nonces
  • Promo codes (orthogonal to logical intent)

2.3 Three-Layer Defense Architecture

┌─────────────────────────────────────────────────────────────┐ │ Layer 1: Pre-check (fast path) │ │ • Query master_orders by idempotency_key │ │ • Legacy (NULL fingerprint) → return existing immediately │ │ • DRAFT → fall through (incomplete, allow re-checkout) │ │ • Non-legacy + no active cart → return existing (retry) │ │ • Non-legacy + active cart → fall through to Layer 2 │ ├─────────────────────────────────────────────────────────────┤ │ Layer 2: Post-load fingerprint comparison │ │ • Load cart items, compute fingerprint from live data │ │ • Re-query master_orders by idempotency_key │ │ • Fingerprint match → return existing order │ │ • Fingerprint mismatch → throw 409 Conflict │ ├─────────────────────────────────────────────────────────────┤ │ Layer 3: Catch block (23505 race safety) │ │ • Unique constraint violation caught │ │ • Re-query existing order, compare fingerprints │ │ • Mismatch → throw 409 Conflict │ │ • Match → return existing order │ └─────────────────────────────────────────────────────────────┘

Why Three Layers?

  • Layer 1 avoids expensive cart/offer loading for retries (common case)
  • Layer 2 catches conflicts when an active cart exists with different contents
  • Layer 3 handles the race condition where two concurrent requests pass Layers 1-2 simultaneously — PostgreSQL's unique constraint is the final arbiter

2.4 Conflict Error Format (RFC 7807)

{ "type": "https://errors.scs.local/idempotency-conflict", "title": "Idempotency Key Conflict", "status": 409, "detail": "This idempotency key was already used for a different checkout operation" }

3. P1.1-B — Partial Fulfillment Semantics

3.1 Audit Findings

The Phase 1 report identified that reserveStock uses Math.min(orderedQuantity, availableQuantity), meaning partial reservation is possible. The question: is this intentional or a bug?

Decision: RETAIN partial fulfillment. The existing domain model clearly and intentionally supports partial quantities.

Evidence from Repository

SignalEvidence
FSM StatusPARTIALLY_ACCEPTED exists as a canonical order status with defined transitions
partiallyAcceptOrder()Dedicated method that sets qtyConfirmed per item and recalculates financials (subtotal, VAT, commission, total) based on confirmed quantities
settleStockForStatus()On PARTIALLY_ACCEPTED, releases qtyReserved - qtyConfirmed back to available — proving the system tracks partial holds
Stock settlement tests"releases only what was actually held" — existing E2E verifies partial settlement math
qtyConfirmed fieldPer-item confirmed quantity, independent of qtyReserved and qtyOrdered

3.2 Documented Partial Fulfillment Behavior

Example: Requested quantity: 10 Available stock: 5 ───────────────────────── qtyOrdered: 10 qtyReserved: 5 ← Math.min(10, 5) qtyConfirmed: 5 ← after merchant partial acceptance Financial recalculation: Original: 10 × 200 = 2000 minor Confirmed: 5 × 200 = 1000 minor VAT/commission/total recomputed on confirmed amount Stock settlement: reserved (5) - confirmed (5) = 0 released on_hand decreases by confirmed (5)

This is the intended B2B wholesale behavior — merchants confirm what they can fulfill, the system adjusts financials accordingly.

5. Database Migration

Migration 0033

ALTER TABLE master_orders ADD COLUMN IF NOT EXISTS request_fingerprint VARCHAR(64);
  • Backward compatible: Nullable column, no NOT NULL constraint
  • Non-destructive: Existing rows remain NULL (legacy orders returned as-is on key match)
  • Idempotent DDL: IF NOT EXISTS — safe to re-run
  • No index needed: Fingerprint is always looked up via idempotency_key (already indexed)
  • Existing unique constraint preserved: master_orders_idempotency_key_unique unchanged

6. Security

Fingerprint Integrity

  • Server-side computation: Fingerprint is computed from live cart data inside checkout() — never received from the client
  • No client-supplied hash: The client supplies only the idempotencyKey; the server determines the logical request identity
  • Price tampering irrelevant: Even if a client manipulates priceMinor in the cart, the fingerprint uses variantId:quantity:offerId — prices are not part of the fingerprint
  • Offer identity matters: Changing the offer (different seller/pricing) changes the fingerprint → conflict detected

Concurrency Safety

  • Database constraint is the anchor: Application-level checking is a fast path; the unique constraint on idempotency_key is the final safety net
  • No advisory locks needed: The three-layer approach (pre-check → fingerprint compare → 23505 catch) is simpler and equally safe
  • No TOCTOU window: Even if two requests read "no existing order" simultaneously, the INSERT unique constraint catches the race
