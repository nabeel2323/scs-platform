2.1 GAP-1: Mobile Role Gate

AttributeValue
SeverityP1
EffortMedium — ~1 day
AppsMobile
Filesmobile/lib/router/router.dart mobile/lib/providers/providers.dart
Depends onNone
Breaking?No — adds redirect, does not remove routes
StatusImplemented — as specified. profileProvider was already available via the existing providers.dart import, so the extra models.dart import was unnecessary; the redirect also exempts /merchant/register. Passes dart analyze.

Problem

router.dart:36-42 only checks isAuthenticatedProvider. Every route (merchant dashboard, driver scaffold) is reachable by any authenticated user, including BUYERs who get 403 errors on action.

Solution

Add a role-aware redirect in the router's redirect callback. The profileProvider already exposes role from GET /v1/me. Merchant routes redirect non-merchant roles to /home; driver route is hidden until Phase 2.

Patch

mobile/lib/router/router.dart

// Add at top of file:
import '../models/models.dart';

// Inside routerProvider, replace the redirect callback:
redirect: (context, state) {
  final loggedIn = ref.read(isAuthenticatedProvider);
  final goingToLogin = state.matchedLocation == '/login';
  if (!loggedIn && !goingToLogin) return '/login';
  if (loggedIn && goingToLogin) return '/home';

  // Role-based route protection (GAP-1 remediation)
  if (loggedIn) {
    final profileAsync = ref.read(profileProvider);
    final role = profileAsync.maybeWhen(
      data: (p) => p.role,
      orElse: () => null,
    );
    final isMerchant =
        role == 'MERCHANT_OWNER' || role == 'MERCHANT_STAFF';
    final path = state.matchedLocation;

    // Merchant routes require merchant role
    if (path.startsWith('/merchant') && !isMerchant) {
      return '/home';
    }
    // Driver route hidden until DRIVER role exists (GAP-7)
    if (path.startsWith('/driver')) {
      return '/home';
    }
  }
  return null;
},
Note

The profileProvider is a FutureProvider. During initial load, maybeWhen(orElse:) returns null, so the redirect does not fire until the profile is loaded. This avoids a flash of redirect for legitimate merchant users. If the profile fails to load, the server's 403 on the API call remains the fallback.

Testing

  • Negative: Login as BUYER → navigate to /merchant → expect redirect to /home
  • Negative: Login as BUYER → navigate to /driver → expect redirect to /home
  • Positive: Login as MERCHANT_OWNER → navigate to /merchant → expect dashboard renders
  • Positive: Login as MERCHANT_STAFF → navigate to /merchant/catalog → expect catalog renders
  • Edge: Login as BUYER → navigate to /merchant/register → expect registration page (open path, any user can become merchant)

Step 1: Add hasPerm helper

apps/web/src/lib/auth.ts

/** Check if the current user has a specific permission key. */
export function hasPerm(perm: string): boolean {
  const perms = getUser()?.perms ?? [];
  return perms.includes(perm);
}

/** Check if the current user has ALL specified permission keys. */
export function hasAllPerms(perms: string[]): boolean {
  const userPerms = getUser()?.perms ?? [];
  return perms.every(p => userPerms.includes(p));
}

3.4 GAP-6: Analytics Write Endpoint Guard

AttributeValue
SeverityP2
EffortSmall — ~0.25 day
AppsAPI
Filesapps/api/src/modules/analytics/analytics.controller.ts
Depends onNone
Breaking?No — adds guard to previously unguarded endpoints
StatusImplemented (Option A) — new analytics:track key granted to all six roles; both write endpoints guarded. See the As-Built note below.

Problem

analytics.controller.ts:20-48 exposes POST track and POST track/batch with JWT authentication only (no @RequirePermission decorator). Any authenticated user can emit analytics events.

Solution

Two options depending on design intent:

Option A: Permission guard (recommended if tracking should be controlled)

apps/api/src/modules/analytics/analytics.controller.ts

@RequirePermission('analytics:track')
@Post('track')
async trackEvent(...) { ... }

// Also add to seed.ts:
// New permission key: { key: 'analytics:track', name: 'Track Analytics' }
// Grant to ALL roles (BUYER, STAFF, OWNER, MODERATOR, ADMIN, SUPER_ADMIN)

Option B: Rate-limit only (recommended if tracking is universal)

@Throttle(60, 60) // 60 requests per 60 seconds per user
@Post('track')
async trackEvent(...) { ... }
Design Decision

If analytics tracking is a universal need (all roles emit events), Option B (rate-limit without permission guard) may be more practical. If tracking should be controlled, use Option A. The key risk is event pollution from compromised accounts, which rate-limiting mitigates regardless.

As-Built (implemented — Option A)

Option A was chosen: this is an RBAC-tightening audit and no client currently calls /analytics/track (only docs reference it), so a permission guard carries zero breakage risk. ThrottlerGuard is not wired anywhere in the API, so Option B would have needed extra setup. Implemented as:

  • New analytics:track key added to the PERMISSIONS array in seed.ts and granted to all six roles (SUPER_ADMIN inherits it via PERMISSIONS).
  • POST track and POST track/batch now carry @UseGuards(PermissionsGuard) + @RequirePermission('analytics:track').

Requires pnpm --filter @scs/api db:seed + user re-login so refreshed JWT perms include the new key.

Testing

  • If Option A: Login as BUYER (with analytics:track) → POST track → expect 200
  • If Option A: Login as user without analytics:track → POST track → expect 403
  • If Option B: Send 61 requests in 60s → expect 429 on 61st
