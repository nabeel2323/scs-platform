Boundary rules (enforced, §2.2)

  1. Cross-module calls only via exported application services.
  2. Side effects via outbox_events written in the same transaction — never fire-and-forget.
  3. Cross-module read models built by the consuming module from events.
  4. Public contracts versioned in packages/contracts.
  5. Extraction only on scale divergence, team boundary, or fault isolation (§2.6 rule 5).

CI runs the boundary lint (E6) and fails on violations; each module path has a CODEOWNER.

1.5 API & engineering conventions (§2.5)

  • REST over HTTPS at /v1, JSON, camelCase. Errors are RFC 7807 with a stable type URI per error family.
  • Idempotency-Key required on checkout, all order state transitions, and (P3) payment intents — Redis-backed 24 h store.
  • Cursor pagination; whitelisted filters; optimistic concurrency via If-Match ETag on catalog/admin mutations.
  • Rate limits: Redis token bucket with X-RateLimit-* headers; OTP additionally throttles by phone number.
  • Trunk-based branching; short-lived PRs (< 400 lines, reviewed < 24 h); Conventional Commits; release branches per Flutter flavor. main is always deployable.

2.2 Database conventions (§3.2)

-- canonical table header (every table)
id          uuid primary key,          -- UUIDv7 generated in the application layer (E2)
created_at  timestamptz not null default now(),
updated_at  timestamptz not null default now()
  • PostgreSQL 16 + PostGIS 3.4; all timestamps timestamptz UTC.
  • Money: bigint minor units + ISO char(3) currency. No floats. One active currency per market at MVP.
  • Statuses: varchar + CHECK. JSONB only for rule payloads — never for queryable core fields. Soft delete only where restore is a product need.
  • UUIDv7 is app-generated (PG16 lacks it natively); time-ordered keys keep B-tree locality and cursor pagination cheap (§7.2 #6).
  • Migrations: drizzle-kit generate → hand-review → CI check (lock_timeout, no implicit rewrites) → staging → prod window. Forward-only; immutable once merged.
  • Indexes: FK by default; partial on hot queues; GIN on tsvector; GiST on geography. Monthly RANGE partitions per §3.12.

2.5 Media pipeline (§3.5)

  1. Client requests POST /v1/media/presign with filename, contentType, sizeBytes.
  2. API validates the type/size whitelist (images ≤ 10 MB) and returns a presigned S3 PUT URL + object key.
  3. Client uploads directly to S3 — media never traverses the API.
  4. Client commits the object key; API enqueues a post-processing job (Redis stream).
  5. Worker produces renditions: 200/600 px thumbs, WebP + AVIF, blurhash; strips EXIF; sniffs mimetype.
  6. Worker writes product_media rows (url, thumb, blurhash, alt_text).
  7. CDN invalidates on update; immutable long-lived cache headers.

4.2 Implementation pattern

Every transition is a single transactional unit: guard → mutate → history row → outbox row → idempotency record.

async transition(orderId: string, to: OrderStatus, actor: Actor, reason?: string, idemKey?: string) {
  return this.db.transaction(async (tx) => {
    await this.idem.seenOrReplay(idemKey, tx);                 // 1. idempotency
    const order = await tx.repo.orders.lockForUpdate(orderId);  // 2. row lock — no lost transitions
    const guard = this.fsm.guard(order.status, to);             // 3. FSM guard — only transition source
    if (!guard.allowed) throw new InvalidTransitionProblem(order.status, to);
    await guard.sideEffects(tx, order, actor);                  // 4. stock, re-price check, webhooks
    await tx.repo.orders.setStatus(orderId, to);
    await tx.repo.statusHistory.insert({ orderId, from: order.status, to, actor, reason });
    await tx.repo.outbox.insert({                               // 5. exactly one event
      aggregateType: 'order', aggregateId: orderId,
      eventType: 'order.status.changed',
      payload: { orderId, from: order.status, to, at: new Date() },
    });
  });
}

Rules encoded once, reused everywhere: no controller calls repo directly; no transition bypasses transition(); the FSM guard table lives in orders/fsm.ts as data — the matrix above is executable documentation.

4.3 Policies

  • Re-price guard (I2): if the merchant’s price list changed between checkout and acceptance, the acceptance endpoint returns 409 price_changed with per-line deltas; the merchant explicitly confirms each changed line (POST /orders/{id}/items/{itemId}/confirm).
  • Idempotency: transition endpoints accept Idempotency-Key; replays return the original result, never a second transition (Source §30.3).
  • SLA timers: delayed job fires at sla_at − 2h (warning) and at sla_at (auto-CANCELLED, reason SLA_EXPIRED, buyer notified).
  • Partial cancellation: only the affected sub-order changes; master_orders.status is derived (worst-of).
  • Dispute window: 72 h from DELIVERED; opening a dispute freezes order_financial_breakdown.finalized_at (P3: freezes settlement lines).
