Capacity Analysis at a Glance

Design peak concurrency grows from ~250 concurrent users in the Phase 1 pilot to 20,000–50,000 across regional cells in Phase 7 — a ~200× increase absorbed mostly by extraction and regionalization, not by re-architecture. Volumes below are modeling assumptions consistent with the staged, density-first strategy; they must be re-baselined at every KPI phase gate (Plan §6.x, Source §34.2).

Storage math — Phase 4 hot data

orders 12k/day × ~22 rows × 1.2 KB ≈ 320 MB/day ≈ 115 GB/yr → ×2 for indexes/WAL ≈ 230 GB + analytics events hot 60 days × 1.5 GB ≈ 90 GB + driver_locations 90 days × 250 MB/day ≈ 22 GB + backups/WAL 7-day ≈ 150–300 GB = ~600–800 GB hot → provision 2 TB for 3-year headroom

Write IOPS math

peak orders/hour = 15% of daily → Phase 4: 15,000 × 0.15 ÷ 3,600 = 0.63 orders/s × ~35 transactions each (items, history, outbox, financial breakdown, ledger) ≈ 22 tx/s × ~15 random IO per indexed transaction ≈ < 1k IOPS from orders

The 12–16k provisioning absorbs checkpointing, vacuum, and location writes simultaneously.

Connection math — Phase 4

12 pods × 20 pool = 240 client connections → PgBouncer transaction-mode multiplexes into 60–80 server connections — well under a 400-connection ceiling on 64 GB RAM

4Scalability Path — Phase 1 → Phase 7

4.1 The scaling ladder

Each rung is a deliberate, reversible step — never a re-architecture. Extraction follows the doctrine of Plan §2.6 rule 5: only on proven scale divergence, team boundary, or fault-isolation need.

STAGE 0

Redundant Monolith

Phase 1

2–3 pods behind a load balancer; PG primary + streaming replica; Redis cache tiers. Blue-green deploys from day one (Plan §2.4, §3.3).

STAGE 1

Optimize the Single Database

Phase 2

PgBouncer; monthly partitions on driver_locations; partial hot-queue indexes; read offload to the replica (Plan §3.2).

STAGE 2

Asynchrony & High Availability

Phase 3

Outbox-driven workers (webhooks, settlement); streaming-replica failover becomes mandatory once money moves (Plan §2.6, §6.3).

STAGE 3

First Extractions

Phase 4

OpenSearch (search) and the event-pipeline service + warehouse (analytics) move out; Socket.IO scales horizontally via the Redis adapter (Plan §3.4, §6.4, §2.6 rule 5).

STAGE 4

Ads Pipeline

Phase 5

Dedicated ad-event ingestion (partitioned ad_events behind its own service); Kafka-class bus carries the outbox dispatcher (Plan §6.5, §4.11).

STAGE 5

AI Service

Phase 6

Thin standalone AI service consuming platform events; A/B framework + batch scoring behind the provider-agnostic AI Gateway (Plan §6.6).

STAGE 6

Regionalization

Phase 7

Per-city cells (API + PG + Redis + OpenSearch per region), global control plane, public API gateway with rate limits, optional Citus-style sharding (Plan §6.7).

4.4 The honest constraint analysis

Counter-intuitive finding. The PostgreSQL write path is not the binding constraint through Phase 6: even Phase 7’s peak order load (120k/day × 15% peak hour = 5 orders/s × ~35 tx = ~175 tx/s) fits comfortably inside a 32–64 vCPU instance’s ~2–4k tx/s envelope — provided the event pipeline, ad events, and location ingestion have been extracted per the triggers above.

The real scaling pressures arrive in this order:

① Search (P4)→ ② Event volume (P4–5)→ ③ Location ingestion (P2–3, flagged early)→ ④ Read fan-in (replicas, P4+)→ ⑤ Regional latency (P7 cells)

This is exactly the profile the plan anticipates with its “extract only on proven need” doctrine (§2.6 rule 5) and its explicit Phase 1 fence — no microservices estate (§6.1, Source §21.5, risk R4 “premature complexity”).
